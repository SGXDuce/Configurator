## Core principles this schema follows (already decided, not re-litigated)

- Flat pane list per elevation, not the internal split tree. The tree (split/sashSplit nodes, assemblyPresetRef, etc.) is editing-session bookkeeping — nobody downstream needs to know how a pane was built, only its final geometry and type.
- Configurator's own type vocabulary, not pre-mapped to any consuming tool's buckets (hinged, horizontal-slider, etc. stay as-is). Each consumer — AS 1288 now, pricing later — does its own translation. This matches §6.1's existing rule: derivation logic runs on the receiving end, never baked into the configurator itself.
- productClass is exported exactly as stored ('door' or 'window' — 'side-panel' is never set by the configurator, per §6.3/§6.4, and is not expected in this export). The sidelight/side-panel determination itself is the receiving tool's job, using the position data this schema provides.
- Position is measured from each elevation's own main origin — the bottom-left corner of the outer frame (not the opening), same point already used on-screen for dimensioning. X increases rightward, Y increases upward (opposite of the app's internal top-down drawing coordinates — this is a real conversion the export code has to do, not a relabel). Each pane's position is its own bottom-left corner — this makes the Y value directly usable as "height above floor" once the receiving tool adds its own FFL offset, with no separate "which edge" decision needed on their end.
- **`widthMM`/`heightMM` are the panel in isolation — its full made size, independent of the configuration it's in — not the drawn on-screen footprint (batch 48).** Person-confirmed definition. `visibleGlazedAreaM2` is that panel's own area minus its own rails and stiles — `glazedAreaM2()`'s calculation itself was always correct; the batch-48 bug was purely in the panel SIZE fed into it for sliding-window/door assemblies (see the tuck-in note below), never in the glazing deduction. `xMM` is the physical start of that real panel, including any part that runs into a jamb — for a sliding-window/door assembly this can differ from where the drawn geometry starts.
- Always the true main origin, never a custom origin the person may have placed on screen for their own convenience while drawing (customOrigin is a display aid, not this export's reference point).
- **`unframedEdges`/`unframedEdgeCount` mean structurally unsupported** — no frame member (jamb/head/sill), no sash, and no structural silicone joint holding that edge — not merely "no sash material present." This distinction matters for Case 4 (batch 45/46, below): an edge can be sash-free without being unsupported (an ordinary `O` next to an ordinary `X` has no sash of its own there, but the neighbouring `X`'s real sash genuinely frames it), and conversely a sash-free edge only becomes reportable as unframed when nothing else is holding it either. **(batch 47)** `unframedEdgeCount` is the older, rougher of the two measures — it only ever summed Cases 1–3 (below) and was never updated to include Case 4 or the sashless top/bottom exception, so it does not follow the structural definition above exactly in every case. `unframedEdges` is the one that does, including both of those corrections — see its own field note below, and the "AS1288 reads `unframedEdges` only" note further down. Unframed-edge count draws from three separate sources, not one:
  - The pane's own sash*Locked flags (Case 2 — flat silicone joint to a neighbouring pane, batches 23–24).
  - Whether the pane's outer-touching edge coincides with a meeting-tagged jamb on the elevation (Case 1 — angled join, batch 26). This does not set sash*Locked on the pane at all — it's a separate mechanism, geometrically checked the same way leavesTouchingJamb() already does for the angled-join blocking rule. Missing this source would silently undercount every Case-1 pane.
  - **(Batch 30) A `type:'fixed'` pane's outer-touching edge on an elevation with `hasFrame:false`** (Case 3) — that edge has no jamb (frame is off) and no sash (fixed has none), so it's genuinely unframed even though it's neither a silicone joint nor a meeting-tagged edge. Guarded per-side against double-counting an edge that's ALSO meeting-tagged (Case 1 already counts that one). Only fires for `fixed` — every other type has its own real sash regardless of `hasFrame`. Export-only: the configurator's own live editing still allows `hasFrame:false` freely with no on-screen warning; this only affects what gets reported downstream.
- Frame length is a real sum, not a per-pane figure alone. Three components, added together (see "Frame length calculation" below) — AS 1288 doesn't need this field at all, but pricing will, so it's computed now while the geometry is fresh, per your own call.
- **(v2, batch 39; matching rule corrected batch 40; tolerance corrected batch 41)** The cross-elevation pane link is NOT a stored field anywhere — no new tree-node field, no UI to create/manage/edit it. It's computed fresh, directly from geometry, every single time an export is produced, so there's nothing to go stale. Each side's meeting-tagged jamb is found independently (never assumed to be jambL on one elevation and jambR on the other). Panes are matched by their actual edge position along the jamb (both start and end, within `PANE_EDGE_MATCH_TOL_MM`, 1mm) — NOT by sorted order and array index alone, which batch 39 originally did and batch 40 found to be a real bug (two elevations with the same pane count in the same order can still have misaligned edges). Any pane with no matching partner blocks the ENTIRE export — see "Export blocked on an unmatched meeting-jamb pane" below.
- **(v2, batch 39)** `angledJoinAngleDeg`/`angledJoinType` (batches 35/36) were deliberately held out of `system` until this pane link could ship alongside them, per this doc's own earlier note — both are now real, documented `system`-level fields, not stubs.
- **(v4, batch 44)** `unframedEdgeCount` sums three sources without saying which specific edges they are — AS 1288 needs the specific edges (Table 5.3 for vertical/jamb-side edges vs. a different clause for horizontal edges), not just a count. `unframedEdges: {top, bottom, left, right}` is the same three-source computation as `unframedEdgeCount`, mapped per-edge instead of summed — see the `unframedEdges` field note below for the two places the two fields deliberately disagree.
- **(batch 45, no schemaVersion bump — a correctness fix to the existing v4 shape, not a new field)** Two corrections, both scoped to sashless sliding-window presets only. First, `buildAssemblyPresetTree` (the underlying preset builder, not this export layer) had wrongly given a sashless `O` (`type:'fixed'`) leaf `SASHLESS_STILE_MM` on its left/right sash edges — a bare `fixed` pane has no sash material at all, so it's now zero on all four edges, matching an ordinary non-sashless `O`. Second, a new Case 4 on `unframedEdges` (only — `unframedEdgeCount` is deliberately untouched) flags a sashless `O`'s edge at an internal overlap join (touching a sashless `X` sibling) as unframed, since that edge now genuinely has no sash.
- **(batch 46, no schemaVersion bump)** Corrects which panes carry `sashless: true` at all, based on the physical product as confirmed directly by the person, not derived from the code: **a sashless `O`'s top, bottom, AND outer jamb edge are all genuinely frame-supported — only its inner vertical edge (facing a sashless `X`) is unsupported**, since there's no channel, rebate, bead, or silicone there at all. At the time, `sashless: true` was understood to mean "this pane's horizontal edges are unsupported, route to AS1288 Clause 5.15" — true for a sashless `X`, false for a sashless `O`. **(Correction, batch 61 — see the `sashless` field note below for the current, accurate definition.)** That "horizontal edges unsupported" phrasing was itself only ever correct for a sashless double-hung sash (`vertical-slider`) — for a sashless sliding-window `X` (`horizontal-slider`) it was backwards from the start: an `X`'s real `sashEdgesMM` has always put zero material top/bottom and real material left/right, meaning its genuinely free/unsupported edges are top/bottom, not left/right. This was a latent misstatement in this document, not a code bug — nothing in the actual export was ever driven by that sentence — first identified and corrected in batch 61. `O` no longer carries the flag at all (still keeps its all-zero sash from batch 45, unchanged). Case 4's own gate is corrected to match: it now checks whether the *matched overlap-join neighbour* is sashless (`node.type === 'fixed'` for this leaf, the neighbour's own `node.sashless === true`), not whether this leaf itself is sashless — since `O` is never sashless as a concept any more. A `rawState` blob saved before this batch may still have `sashless: true` on an `O`; `restoreFromRawState()` now strips it from any `type:'fixed'` leaf on load (no `rawStateSchemaVersion` bump — the leaf shape itself hasn't changed, only which leaves are allowed to carry the flag). See the `sashless` and `unframedEdges` field notes below for the full corrected boundary.
- **AS1288 reads `unframedEdges` only and ignores `unframedEdgeCount`.** `unframedEdgeCount` is kept for backward compatibility/other potential consumers (e.g. a future pricing tool that just wants a raw count) but is not the field AS1288's own routing logic is built against — `unframedEdges`'s per-edge shape is the one with the Case-4/sashless corrections that make it physically accurate.
- **(batch 48, no schemaVersion bump — a correctness fix to `widthMM`/`xMM`/`areaM2`/`visibleGlazedAreaM2`/`frameLengthMM`, not a shape change)** A sliding-window (or sliding-door — confirmed to share the identical mechanism, not assumed) assembly's own row-level frame tuck-in was being absorbed entirely into the DRAWN geometry of whichever leaf(s) land on the remainder side of the tree's own internal folds — e.g. an ordinary `OX-win` in a 910mm opening drew its `O` at 435mm wide when its real, entered panel width was 475mm. `buildExportElevation` now computes each such leaf's real panel `{x, w}` in a separate correction map (never mutating the drawn leaves themselves) and uses it only for `widthMM`, `xMM`, `areaM2`, `visibleGlazedAreaM2`, and `frameLengthMM`'s sash-perimeter term. **`unframedEdgeCount`, `unframedEdges` (including Case 4's own x-range overlap test), meeting-jamb touch detection, and the cross-elevation pane link all keep running on the original drawn geometry, completely unaffected** — confirmed by diff, not just by intent. See the "Real panel size for sliding-window/door assemblies" section below for the full derivation and per-pattern trace.
- **(batch 49, no schemaVersion bump — a correctness fix to the same fields as batch 48, not a shape change) A sliding pane's `widthMM` now comes from the panel width stored on its leaf when the preset was confirmed, not from the drawn geometry.** Batch 48 derived every `O`'s real width as (the first `X`'s drawn width) − 60, which only holds when the entered widths equal the prefill defaults. The preset form has a separate width per section and validates only the total, so custom widths are legal: an ordinary `OX-win` at 910mm entered as O=500/X=510 exported O=450, and a pattern with unequal `X` widths (e.g. `OXXO`) exported every `X` at the first `X`'s width. Each sliding-assembly section node now carries `panelWidthMM` (its entered width, re-stamped on every "Edit assembly widths" confirm), and export reads it directly. `xMM` placement is batch 48's rule unchanged, driven by the stored widths. A `rawState` saved before batch 49 has no `panelWidthMM`, so its export falls back to batch 48's reconstruction. `unframedEdges`/`unframedEdgeCount` (including Case 4), meeting-jamb detection, and `linkedPaneId` still use the drawn geometry and are identical before and after (checked by comparing real exports across 11 sessions).
- **(batch 51, no schemaVersion bump — a correctness fix to the same fields as batches 48/49, not a shape change) A sliding section can be subdivided (a transom or a vertical bar, any nesting depth) — batch 49's per-section `panelWidthMM` stamp couldn't survive that.** Splitting a section replaces its node, so the stamp was silently lost the moment a section was subdivided: the export correction's own leaf-count check then found more leaves than the pattern had letters and bailed out with NO correction and no warning — the whole row exported drawn, tuck-in-absorbed widths. Storage moved to the assembly's own marker (`panelWidthsMM`, plural, an array in pattern order, alongside the existing `pattern`/`productClass`/`id`) instead of a per-section stamp, and the correction is now computed per SECTION (which may be a whole subdivided subtree) rather than per leaf — see "Real panel size for sliding-window/door assemblies" below for the corrected derivation, the person-confirmed construction assumption behind it, and the stated drawn-position interpretation for a bar inside a panel. A `rawState` saved before batch 49, or between batches 49 and 51 (neither shape has `panelWidthsMM` on the marker), falls back to batch 48's reconstruction exactly as before — `rawStateSchemaVersion` is not bumped. `unframedEdges`/`unframedEdgeCount` (including Case 4), meeting-jamb detection, and `linkedPaneId` are unaffected — still computed from the original drawn geometry throughout, confirmed unchanged for every unsubdivided case tested. **Investigated, not fixed: two on-drawing edit paths can change a sliding assembly's section widths without going through "Confirm resize" at all, leaving `panelWidthsMM` stale** — see "Known gap: on-drawing edits can leave panelWidthsMM stale" below.
- **(batch 48) Sashless double-hung's overlap no longer wrongly includes the frame tuck-in.** `getDoubleHungOverlapMM()` previously added `FRAME_TUCKIN_MM` regardless of sashless-ness; a sashless double-hung unit has no top/bottom tuck-in at all (its own tuck-in-driving sash is already zero), so the overlap is now `DOUBLE_HUNG_OVERLAP_MM` (60mm) only when sashless, vs. `DOUBLE_HUNG_OVERLAP_MM + FRAME_TUCKIN_MM` (100mm) for an ordinary unit with the frame on. This affects the actual built tree (bottom pane height), the top-height prefill, and the reopen-adjacent validation formula — all three now consistently read the same corrected value, same "single source of truth" precedent batch 21 established for the ordinary case. Ordinary (non-sashless) double-hung is completely unaffected.
- **(batch 48, flagged, not addressed) Sliding panel height is still exported as the opening height.** Whether a sliding panel's real height runs into the head/sill tracks the same way its width runs into the jambs is unconfirmed — `heightMM`/`yMM` for every sliding-window/door pane are untouched by this batch. See "What's deliberately NOT in this version" below.
- **(v5, batch 55)** `unframedEdges` said WHICH edges are unframed but not why — every downstream question of "is this genuinely a Case 4 next-to-sashless situation, or an angled join" required re-deriving it from other fields. New `unframedEdgeReasons: {top, bottom, left, right}`, one of `'angled-joint'` (Case 1), `'silicone-flat'` (Case 2), `'frame-off'` (Case 3), `'next-to-sashless'` (Case 4), or `null` when framed — with the invariant `unframedEdgeReasons[edge] === null` iff `unframedEdges[edge] === false`, verified across every session this batch drove headlessly (not just the two field-notes example already exercised). `buildExportElevation` now routes every one of Cases 1–4 (including the sashless top/bottom exception) through a single convergence point, `setUnframedEdge(edge, reason)`, which defensively throws — naming the pane id, the edge, and both reasons — if two Cases ever disagree about the same edge, rather than silently keeping whichever ran last (same "throw rather than guess" convention as `computeSlidingAssemblyLeafCorrections`, batch 51, and `isPanelWidthsStale`, batch 52/53). **Investigated, not just assumed:** Case 2 (`sash*Locked`) and Case 4 (fixed pane next to a sashless overlap neighbour) were checked directly against the code, not the schema doc's own prose, for whether they can ever collide on the same edge — they can't, confirmed by tracing `confirmUnframedJoint`/`confirmSplit`'s own `MIN_PANE_MM` interior-position guarantee against Case 4's genuine-overlap detection; see `unframedEdgeReasons`' own field note below for the full argument (which also corrects a wrong premise: `sash*Locked` is NOT restricted to panes with a real sash — `confirmUnframedJoint`, batch 24, sets it on `type:'fixed'` panes directly).
- **(v6, batch 61 — documentation/labeling batch, no numeric export value changes anywhere)** Removes the old sashless top/bottom EXCEPTION (batch 44, scope-corrected batch 46 — see its own now-superseded description a few bullets above) and replaces it with a new, additive **Case 5**, `'sashless-free-edge'`: any leaf with `node.sashless === true` now gets `setUnframedEdge` calls on a specific pair of opposite edges — **left+right for a `horizontal-slider`, top+bottom for a `vertical-slider`.** The horizontal-slider direction is DELIBERATELY the physically backwards one (see the `sashless` field note and the new "Sashless free-edge flag (Case 5, batch 61)" section below for the full reasoning) — it intentionally matches `sashEdgesMM`'s own currently-wrong left/right capping placement for a sashless X, not the pane's real free edges (which are genuinely top/bottom). The vertical-slider (double-hung) direction is the physically correct one, and already matched `sashEdgesMM`'s own top/bottom-zero orientation before this batch. `schemaVersion` bumped 5→6 despite no new field, because the MEANING of `unframedEdges`/`unframedEdgeReasons` changed for a sashless pane under the same shape (a real behavioural change for any existing consumer reading those two fields against a sashless pane) — see "postMessage embed protocol" below for the matching `ready` handshake bump. **`unframedEdgeCount` is untouched** — Case 5 is a third, distinct kind of divergence between it and `unframedEdges`, on top of the two that already existed (Case 4 added batch 45, never summed into `unframedEdgeCount`; and the now-removed sashless exception, which used to suppress a flag `unframedEdgeCount` never set in the first place) — see the `unframedEdgeCount` field note below. **Collision-checked against Cases 1–4** (not assumed) — see the "Case 2/Case 4 mutual exclusivity" section below, extended with a new subsection for Case 5. `SASHLESS_STILE_MM` split into `SASHLESS_HSLIDER_CAPPING_MM`/`SASHLESS_DH_CAPPING_MM` (same 10mm value, split purely so each call site can carry its own orientation-correctness comment) — no numeric change. The sliding-window sashless preset checkbox label changed to describe the physically-correct intended orientation (see "Real panel size for sliding-window/door assemblies" section's sibling note below); the double-hung checkbox label is unchanged (already correct for that family's own real orientation). ~~DO NOT CONSUME V6 SASHLESS HORIZONTAL PANES FOR REAL NUMBERS UNTIL THE NUMBERS BATCH.~~ **Superseded by batch 63 — see the "Numbers batch (batch 63)" section below: `sashEdgesMM`'s own left/right placement was swapped to top/bottom that batch, resolving the disagreement this bullet describes. v6 sashless horizontal-pane numbers are now final and safe to consume.**

## Known gap: `setUnframedEdge`'s collision guard has never actually fired (batch 55/56, extended batch 61)

The defensive throw in `setUnframedEdge` (the convergence point all five Cases go through as of batch 61 — see the field note above and the "Case 2/Case 4 mutual exclusivity" writeup and its own batch-61 Case-5 extension) exists to catch two Cases disagreeing about the same edge. As of batch 55/56, it had **zero live evidence behind it**: instrumented logging across the 3 real verification sessions this project had driven at the time (the main two-elevation session plus sessions A and B, all in the schema example above) recorded 9 total `setUnframedEdge` calls, and every single one had `prevReason: null` — meaning no edge was ever set twice in any of those sessions, let alone by two disagreeing Cases. **Batch 61 does not change this state** — the 10 real headless sessions driven for batch 61's own verification (see `Configurator_Project_Summary.md`'s batch-61 entry) likewise recorded no collision. All ten Case-pairings across five Cases (1-vs-2, 1-vs-3, 1-vs-4, 1-vs-5, 2-vs-3, 2-vs-4, 2-vs-5, 3-vs-4, 3-vs-5, 4-vs-5 — batch 55/56 only had the six pairings across Cases 1–4; batch 61 adds the four new pairings involving Case 5) rest entirely on the code-traced arguments below and in the "Case 2/Case 4 mutual exclusivity" section's Case-5 extension, not on exercised behavior — **with one explicitly-flagged exception: the 1-vs-5 pairing for `vertical-slider` top/bottom is proven safe only by the current UI's lack of a head/sill meeting-edge control, not by a data-shape argument the other nine pairings all have.** If any of the data-shape arguments have a hole, or if a future batch adds head/sill meeting-edge UI without re-deriving the 1-vs-5 pairing, nothing in this project's own test history would catch it before the throw itself fires in real use.

**The argument's actual shape, not just its conclusion:**

- **Case 1/3 vs Case 2** — already covered above ("Case 2/Case 4 mutual exclusivity"): Case 2's edge is always a brand-new interior boundary a split just created (strictly between the region's two original outer edges, enforced by `confirmUnframedJoint`/`confirmSplit`'s own `MIN_PANE_MM` check), while Case 1/3 only ever fire on a pane's original outer-boundary edge. An interior edge and an outer-boundary edge can never be the same edge.
- **Case 1/3 vs Case 4, top/bottom** — trivially excluded, not by geometry but by code shape: Case 4's own `setUnframedEdge` calls are gated to `'left'`/`'right'` only (`if (oCenterX < lCenterX) setUnframedEdge('left', ...) else if (oCenterX > lCenterX) setUnframedEdge('right', ...)`) — Case 4 never calls `setUnframedEdge('top', ...)` or `setUnframedEdge('bottom', ...)` at all, so it cannot collide with Case 1/3 on those two edges regardless of any geometric argument.
- **Case 1/3 vs Case 4, left/right** — this is the one that needs geometry, and it needs the invariant below: **every leaf's `x` and `x + w`, as `collectExportGeometry` produces them, stay within `[0, openingW]`.** Traced through both of `collectExportGeometry`'s recursive branches (not assumed):
  - **Plain `split` branch:** for a v-axis split, `leftW = max(0, posMM − thicknessMM/2)` and `rightW = max(0, w − posMM − thicknessMM/2)`. The left child gets `{x, leftW}`; the right child gets `{x + leftW + thicknessMM, rightW}`. Its own right edge is `x + leftW + thicknessMM + rightW`, which — whenever neither `max(0, ...)` clamp bites — algebraically reduces to exactly `x + w`, the parent's own right edge. So a plain split never lets either child's bound exceed the parent's; by induction from the root call (`collectExportGeometry(ev.root, 0, 0, openingW, openingH, ...)`, i.e. `[0, openingW]`), every plain-split leaf stays inside `[0, openingW]`.
  - **`sashSplit` branch:** for a v-axis sash split, the two children are sized `sashSizeMM` and `remSize = max(0, w − sashSizeMM + overlapMM)`, positioned so that whichever child is NOT the sash-side one has its outer edge land exactly on the parent's own outer edge (`fromEdge:'start'`: child1's `x + w` reduces to the parent's `x + w`; `fromEdge:'end'`: child0's `x` is the parent's own `x`, and child1's `x + w` is again the parent's own `x + w`). The sash-side child's own outer edge sits `sashSizeMM` in from the parent's edge on `fromEdge:'start'`, or up to `overlapMM` past the remainder child's edge on `fromEdge:'end'` — in both cases strictly inside the parent's span, since `sashSizeMM`/`overlapMM` are always a fraction of the row's own real content width by construction (`buildSlidingWinOverlapTree`'s own `MIN_PANE_MM`-guarded solve), never larger than the span they're carved from. So a sashSplit also never lets a child's bound exceed the parent's.
  - Since both branches preserve `[x, x+w] ⊆ [parent's own x, x+w]` at every recursion step, and the root call starts at exactly `[0, openingW]`, every leaf `collectExportGeometry` ever produces has `x ≥ 0` and `x + w ≤ openingW`.
  - Case 1/3 only ever fire when THIS leaf's own edge sits at that outer boundary (`x ≈ 0` for `left`, `x + w ≈ openingW` for `right`, within `EDGE_TOUCH_EPS_MM`). Case 4 requires a DIFFERENT leaf (the sashless neighbour) whose own x-range extends past this leaf's edge on the outward side — i.e. a neighbour with `x < 0` (to collide with a Case-1/3 `left`) or `x + w > openingW` (to collide with a Case-1/3 `right`). The invariant above makes both impossible: no leaf, including that hypothetical neighbour, can ever have a bound outside `[0, openingW]`. So Case 4 can never fire on an edge Case 1/3 has already claimed.
- **Case 2 vs Case 3** — same interior-vs-outer argument as Case 2 vs Case 1: Case 3 is also strictly an outer-boundary check (`hasFrame:false`, edge at `x ≈ 0`/`x + w ≈ openingW`), and Case 2's edge is always interior.

**Was the `[0, openingW]` invariant itself ever checked before this batch?** No — grepped the whole file for `assert`/`console.assert`/any test-harness pattern; there is none. This project's only verification mechanism has always been the per-batch headless-Chrome sessions recorded in this document and the project summary, and none of them instrumented or asserted this specific bound — it has lived as an unstated, unverified assumption underneath the geometry since `collectExportGeometry` was written, and now, as of this batch, it's load-bearing for the collision-guard proof above. **Checked for the first time this batch:** a one-off headless-Chrome script called `collectExportGeometry` directly (bypassing the UI, using the app's own `buildAssemblyPresetTree`/`buildDoubleHungUnit` builders) against every confirmed sliding pattern (`OX`, `XO`, `OXX`, `XOX`, `OXXO`, `OXXX`; even, uneven-ascending, uneven-descending, and alternating section widths; sashless and framed), several nested multi-level plain-split trees (mixed v/h axis, uneven mullion thickness, and a deliberately tight thickness-vs-available-space case to stress the `Math.max(0, ...)` clamps), a sliding assembly nested inside a plain split (a realistic real-world layout), and double-hung units (1-3 stacked) — 55 trees, 173 leaves total, zero violations. This is a one-off verification script, run once for this batch and not committed as a permanent regression test (this batch is documentation/labeling only, per its own scope) — the invariant itself remains genuinely untested by anything that runs automatically. A future batch that changes `collectExportGeometry`, `buildSlidingWinOverlapTree`, or `confirmSplit`'s clamping should re-derive or re-test this, not assume this writeup still holds.

## Cross-elevation pane link (v2, batch 39; matching rule corrected batch 40)

Computed fresh at export time, directly from geometry — **not a stored field anywhere in the app's own data model.** There is no new field on any tree node and no UI to create, edit, or remove a link; nothing about it can go stale, because it's recomputed from scratch on every single export.

For each elevation, the algorithm finds whichever of its four `meetingEdges` is actually tagged `'meeting'` (checked independently per elevation — never assumed to be `jambL` on one side and `jambR` on the other, since `addAngledJoin` always tags the two elevations' OPPOSITE jambs, not a fixed pair) and collects every leaf touching that edge. Every leaf touching a meeting-tagged jamb is already guaranteed `type:'fixed', productClass:'window'` by the existing join-creation/edit blocking rule (`leafAllowedAgainstMeetingEdge`), so no type restriction was needed to make matching meaningful.

**Matching is by actual edge position, not by sorted order and array index.** This was found to be a real correctness bug in the original v2 batch (39) and fixed in batch 40, a configurator-side correctness finding — not a change requested by the AS 1288 side. The original approach sorted each elevation's touching panes top-to-bottom and paired them purely by index (first-with-first, second-with-second): that's wrong whenever the two elevations have the same pane count in the same top-to-bottom order but the panes' actual edges along the jamb don't line up — e.g. a transom at 1000mm on one elevation's meeting edge and a transom at 1400mm on the other's, with a single pane on each side either side of it. Index-pairing would link panes that don't physically meet at all.

The corrected rule: each touching pane's start and end position along the jamb (its own internal top-down `y` and `y + h` — the same coordinate already used to detect that it's touching the jamb in the first place, not a second coordinate system) must both match — within `PANE_EDGE_MATCH_TOL_MM` — a pane on the other elevation before the two are linked. A plain pane-count mismatch is just one way for a pane to end up with no matching partner under this rule, so it's no longer a separate check — there is one match check per touching pane.

**`PANE_EDGE_MATCH_TOL_MM` (1mm, corrected batch 41) is deliberately a SEPARATE constant from `EDGE_TOUCH_EPS_MM` (0.01mm), not a reuse of it.** Batch 40 originally reused `EDGE_TOUCH_EPS_MM` for this comparison — found to be wrong. `EDGE_TOUCH_EPS_MM` was built for a different, more forgiving question ("does this pane touch the jamb at all," computed from clean subtraction/addition through one elevation's own tree, where 0.01mm exists only to absorb floating-point noise), not "do two independently-computed mm values, from two different elevations' own trees, represent the same physical edge" — where 0.01mm is unrealistically tight for physical timber joinery and risked false-blocking a genuinely valid export over ordinary float drift. `PANE_EDGE_MATCH_TOL_MM` is used only in this one edge-matching comparison; `EDGE_TOUCH_EPS_MM` itself, and every other place it's used (jamb-touching detection, `unframedEdgeCount`), is unchanged.

The common case is exactly one pane per side, which pairs trivially provided their edges do actually align (usually true, since the join creation flow syncs overall height — but not guaranteed, since each elevation's own frame members can still differ). Multiple stacked panes against the meeting jamb on both sides pair by matching height range, not merely by stacking order.

## Export blocked on an unmatched meeting-jamb pane (v2, batch 39; scope widened batch 40)

If any pane touching either elevation's meeting jamb has no matching partner on the other side — whether because the counts differ, or because the counts match but the edges don't line up — **the entire export is blocked**: neither the standalone file download nor the embed `done` message is produced. A clear, persistent, visible in-page error is shown (never a console log or `alert()`), naming the elevation and the specific height range (in mm) that has no match, and the closest candidate found on the other side if any panes touch that jamb at all. As of batch 40 this error shows in two places: the existing top-of-page banner, and a second box directly next to the Export/Done button itself, so the error is visible both from a distance and right at the point of the action that triggered it.

This check runs first, before any part of the export (including `rawState`) is built — a mismatch produces genuinely no export, not a partial or malformed one — and is identical in standalone and embed mode; it isn't an embed-only concern.

## Export block: sashless subdivision and frame-off (permanent, batch 62/63)

**Status: PERMANENT product rule, as of batch 63.** Batch 62 introduced this as a TEMPORARY pre-export gate, pending a decision on how AS1288 should treat a sashless pane's own subdivision or a sashless pane on a frame-off elevation. **Batch 63 confirms both as permanent, by-design product rules, not pending decisions: a sashless slider (either family) permanently CANNOT be built on a frame-off elevation, and permanently CANNOT be subdivided by a bar/transom/mullion.** This was confirmed by the same person who supplied this batch's real `sashEdgesMM` capping figures — see "Numbers batch (batch 63)" above. This is a pre-export GATE, not a schema change — no field is added anywhere in `system`, `schemaVersion` is not bumped (stays 6), and `rawState`'s own shape is untouched. `checkSashlessExportable()` runs first inside `buildExportData()`, before `computeCrossElevationLinks()` — the same "check first, before touching anything else" convention the batch-39/40 cross-elevation mismatch check already uses (see "Export blocked on an unmatched meeting-jamb pane" above) — and returns the same `{ok, error}` shape, routed through the same `buildExportDataOrBlockedError()`/`showExportBlockedError()` wiring both existing blocking checks already use. It is deliberately NOT built the batch-56 way (a throw somewhere deep in the call graph, caught later by message-substring matching) — this is a real, structural, dedicated pre-check with its own boolean result, checked directly against tree shape, not a side effect of some other function's throw. **This remains the ONLY enforcement point — batch 63 deliberately added no defensive/structural UI code elsewhere to prevent building a subdivided or frame-off sashless slider; the UI still allows building these shapes, only export is gated, exactly as batch 62 built it.**

Two narrow, structural trigger conditions, checked over EVERY elevation in the system (not just the currently active one — `checkSashlessExportable` walks each elevation's own `ev.root`/`ev.hasFrame` directly, via a new `nodeAt(root, path)` helper that takes an explicit root, since `getNode(path)` only ever reads the active elevation via closure state):

**Case (b) — frame-off.** An elevation with `hasFrame === false` containing any leaf with `node.sashless === true` anywhere in its tree (`findAnySashlessLeaf`, batch 54's existing generic walk). Blocks.

**Case (a) — subdivided.** A sashless pane's own rectangle has been divided by a bar, transom, or mullion — detected STRUCTURALLY, using each matched preset's OWN expected leaf positions, never a generic "split node with sashless panes on both sides" heuristic (that heuristic would wrongly fire on an OXX preset's own internal overlap join or an OXXO preset's own internal flush join, both of which are ordinary split nodes with a sashless pane on at least one side, by design, since batch 45). Note (batch 63): a NEW sash inset into a section replaces that section's leaf in place (`kind:'filled'` throughout — `makeTypeButton`'s own fresh node literal, confirmed directly against the code), never subdividing it into a `split`/`sashSplit` node — so an inset sash never actually reaches this detection's own "not filled/empty" gate below; it was inaccurately listed alongside "bar/transom" in earlier wording and has been removed from the message text (see "Message" below). For each sliding assembly found via `collectSlidingAssemblyRanges`, each of its pattern's expected section paths (`computeSlidingWinSectionPaths(ref.pattern)`, one array-of-child-indices path per pattern letter, each prefixed by the assembly marker's own path) is resolved against the LIVE tree via `nodeAt`. For each double-hung assembly found via `collectDoubleHungAssemblyRanges`, each unit's path (`collectDoubleHungUnitPaths` — a unit path points AT the unit's own `sashSplit` node itself, confirmed directly against `buildDoubleHungUnit`'s real shape rather than assumed; a unit's two sash leaves are that `sashSplit` node's own two children) has its two child positions (`unitPath.concat([0])` and `unitPath.concat([1])`) resolved the same way. At each resolved position, it's a Case-(a) problem iff ALL of:

- the resolved node is NOT `kind:'filled'` and NOT `kind:'empty'` — something split it further;
- the resolved node has NO `assemblyPresetRef` of its own — excludes a brand-new preset legitimately built to REPLACE that exact expected leaf (the real "Apply assembly preset inside a section" UI action always stamps its own marker directly at the section's own node, so `nodeAt` finds the nested marker's node itself there, which fails this "no ref" test and is correctly excluded — verified directly, see the batch-62 verification writeup in `Configurator_Project_Summary.md`);
- `findAnySashlessLeaf(node)` is true — a sashless leaf survives somewhere under the division (`cloneForSplit`, batch 54, already carries `sashless` onto a split leaf's children, so this is found correctly even several splits deep).

**Deliberately excluded (verified, not assumed) — a transom/mullion:**
- between two whole sashless assemblies,
- between a sashless assembly and an ordinary pane,
- between two ordinary panes,
- inside an OXX/OXXO/DD preset's own internal overlap or flush join (these sit exactly at a preset's own expected leaf positions, but those positions ARE leaves — `kind:'filled'` — so the "not filled/empty" test never fires there in the first place),
- splitting the non-sashless `O` in a sashless OXX/OXX-win (out of scope: `findAnySashlessLeaf` on that leaf position finds nothing, since `O` never carries `sashless:true` — batch 46),
- around any non-sashless assembly, framed or frame-off (out of scope entirely — sashless-only).

None of these ever sit AT one of a preset's own expected leaf positions with a sashless leaf still surviving underneath — they sit ABOVE the marker (between assemblies/panes) or ARE the expected leaf position unsplit (a preset's own internal join). This is why the check is scoped to exactly the marker's own expected positions rather than any split node anywhere in the tree.

**Orphan sashless leaves — counted, not blocked on.** A sashless leaf that isn't at any preset marker's own expected leaf position at all should not be structurally possible (`sashless` is only ever stamped by `buildAssemblyPresetTree`/`buildDoubleHungUnit`, both marker-building code paths), but `checkSashlessExportable` counts it anyway (whole-tree `findAnySashlessLeaf`/count minus the count found at every expected position, across every elevation) and logs it via `console.warn`, rather than trusting the "should not happen" assumption unverified. Confirmed 0 in every one of the batch-62 verification sessions (18 cases, including deliberately awkward ones — a bar splitting the non-sashless `O` in an `OXX-win`, a nested brand-new preset) — see `Configurator_Project_Summary.md`'s batch-62 entry for the exact count.

**Message (reworded batch 63 — permanent-rule wording, replacing batch 62's "not decided yet" framing).** ONE message per export attempt, covering every problem found across every elevation (not one popup per problem — same "collect everything, report once" shape as the batch-40 cross-elevation mismatch message), shown via the existing `showExportBlockedError()` in both the top banner and the box next to Export/Done:

- `"Export blocked: Elevation 1 has a sashless slider divided by a bar. A sashless slider cannot be subdivided — remove the division or build without sashless."`
- `"Export blocked: Elevation 1 has a sashless pane but its frame is off. A sashless slider cannot be built without a frame — turn the frame back on or build without sashless."`

The phrase "or inset sash" (present in batch 62's original wording) has been removed — see the Case (a) note above confirming an inset sash never actually reaches this detection in practice, so its mention in the message was inaccurate. Only the message TEXT changed; `checkSashlessExportable()`'s own detection logic is byte-identical to batch 62.

**Wiring.** Both `downloadExportFile()` (standalone) and the embed `'done'` message handler already route through `buildExportDataOrBlockedError()` → `buildExportData()`, so adding this check at the top of `buildExportData()` covers both call sites automatically — no separate wiring needed at either call site. A blocked export downloads no file in standalone mode and sends no `'done'` message in embed mode, identical in kind to the existing cross-elevation-mismatch block.

This gate is therefore no longer a placeholder awaiting removal or replacement; it is the permanent, correct enforcement of a real product constraint, and should be maintained as such going forward (not "extended or tuned further" in the old temporary sense, but also not scheduled for removal).

## Frame length calculation

Three components summed per elevation:

1. Each pane's own sash perimeter — `2 × (widthMM + heightMM)` for any pane with a real sash (i.e. not `fixed`). A `fixed` pane contributes 0 here. **(batch 48/57)** Uses the real, corrected `widthMM` and `heightMM` for a sliding-window/door pane — see "Real panel size for sliding-window/door assemblies" and "Real vertical (head/sill) panel size for sliding-window/door assemblies" below. **(batch 59)** Uses the real, corrected `widthMM` for a double-hung pane too — see "Real jamb (widthMM/xMM) panel size for double-hung units" below.
2. Real mullions/transoms between panes — walk the split tree once; for every `split` node with `thicknessMM > 0` and NOT `isSiliconeJoint`, add its own length (a vertical mullion's length is the height of the region it divides; a horizontal transom's length is the width).
3. Outer frame — head/sill add the elevation's overall width, jambL/jambR add the overall height, UNLESS that member is off (`hasFrame: false`) or meeting-tagged, in which case it contributes 0.

Do NOT add anything extra for double-hung or sliding-overlap joins. Those panels are already sized wider to include their overlap material — it's already counted in component 1. There is no real separate transom/mullion at an overlap join (confirmed in the project doc itself — the top and bottom sash rails of a double-hung genuinely interlock with nothing between them). Adding a component-2 entry for these would double count.

Known simplification, flagged not hidden: each frame member's length is its full span (e.g. a 1800mm-wide head counts as 1800mm), not the shorter length after mitring the corners. Real corners lose a small amount to the mitre cut, unmodelled here. Accepted for now per your own call — revisit when building the pricing tool properly.

## Real panel size for sliding-window/door assemblies (batch 48)

**The problem.** A sliding-window or sliding-door assembly (`OX-win`/`OXX-win`/`XOX-win`/`OXXO-win`/`OXXX-win` and their door-only equivalents) is drawn on screen with its row's whole frame tuck-in (`FRAME_TUCKIN_MM`, 40mm, or `SASHLESS_FRAME_TUCKIN_MM`, 6mm, for a sashless preset) absorbed entirely into whichever leaf(s) end up on the remainder (non-sash) side of the tree's own internal overlap folds, once that tree is drawn at the true opening width. This is invisible on screen (the drawing is correct — the panel genuinely disappears 20mm into each jamb's own cavity, and `walk()`'s geometry handles that correctly for rendering purposes), but it means the RAW drawn width reported at export time understated the real, physical, made panel size for whichever leaf absorbed the shortfall — e.g. an ordinary `OX-win` in a 910mm opening drew its `O` leaf at 435mm wide, when the real panel entered in the preset form (and actually manufactured) is 475mm.

**Root cause, traced against the actual committed formulas, not assumed:** `computeSlidingWinPrefillWidths` solves exactly ONE scalar real `O` width and ONE scalar real `X` width (`X = O + SLIDING_OVERLAP_MM`) for the WHOLE pattern — every `O` leaf in the assembly shares the same real width, every `X` leaf shares the same real width, regardless of pattern length, run count, or position. `buildSlidingWinOverlapTree` then builds the actual tree using these values as the sash side's own `sashSizeMM` — an absolute value baked in at tree-creation time, never recomputed against whatever region width the tree is later drawn into. This means every `X` leaf's DRAWN width already exactly equals its real width (confirmed by direct trace against all five confirmed patterns) — only `O` needs correcting, and because every `O` in the assembly shares one scalar real width, that real width is simply **(any sibling `X`'s drawn width) − `SLIDING_OVERLAP_MM`**.

Numerically traced (not assumed) across every confirmed pattern, including a flush-joined multi-run case, to confirm no simple per-pattern shortcut works: for `OXXO-win` specifically, the ENTIRE tuck-in shortfall lands on ONE single leaf (the second run's own `O`), not split evenly across both `O`'s the way a naive "half at each jamb" intuition might assume — this is a real, if surprising, consequence of how the committed fold-and-draw mechanism works, not something this batch redesigned or "corrected" toward a more even split. The fix works around this asymmetry entirely, rather than trying to characterise or rebalance it, by deriving every `O`'s real width from a sibling `X`'s drawn width directly.

**`xMM`:** the assembly's own leftmost leaf (in drawn left-to-right order) shifts its start position left by `tuckIn / 2` from its drawn `x` — the real panel genuinely starts further into the row's own left end. This is applied UNCONDITIONALLY whenever `hasFrame` is true, regardless of whether that end of the row happens to touch a true elevation jamb (a sibling pane could sit further left again) — this mirrors `computeSlidingWinPrefillWidths`' own unconditional gating exactly (see its own "leftmost panel's left edge and the rightmost panel's right edge, regardless of panel count" rule, batch 18), not a new assumption introduced by this batch. Every subsequent leaf is then placed left-to-right from that corrected start, using its own corrected real width and the physical adjacency to its left neighbour: an overlap join subtracts `SLIDING_OVERLAP_MM` (the two panels physically overlap by that much), a flush join subtracts nothing (they physically abut) — determined directly by comparing the DRAWN geometry of adjacent leaves (a gap in drawn space means overlap; touching exactly means flush), not by re-deriving `classifySlidingWinJoin`'s own direction logic. Verified numerically: the rightmost leaf's own corrected right edge always lands at exactly `openingW + tuckIn/2` past the true opening boundary, for every pattern traced — confirming the row's own two ends are symmetric even where the WIDTH shortfall wasn't.

**Sliding doors share the identical mechanism** — same `isSlidingOverlapId` gate (pattern-shape based, not `productClass`-based), same `buildSlidingWinOverlapTree`, and the tuck-in was explicitly extended to sliding doors back in batch 18 (its own comment: "the whole overlap/tuck-in mechanism now extends to sliding DOORS too"). This fix therefore applies to sliding-door assemblies automatically, with no separate branch or door-specific logic — confirmed, not assumed.

**Scope: deliberately width/`xMM`/area only.** `unframedEdgeCount`, `unframedEdges` (including Case 4's own x-range overlap test), meeting-jamb touch detection, and the cross-elevation pane link all keep running on the ORIGINAL drawn geometry, completely untouched by this correction — confirmed by diff, not just by intent. `heightMM`/`yMM` were also untouched by this batch — **batch 57 closed that gap; see "Real vertical (head/sill) panel size for sliding-window/door assemblies" below.**

**Batch 49 — where the width now comes from.** The "Root cause" paragraph above describes the prefill (one scalar `O`, one scalar `X` per pattern), but the form doesn't enforce it. It has one input per section and only checks the total (`computeSlidingWinTotalWidth`), so any widths that add up are accepted. Batch 48's "`O` = any `X`'s drawn width − 60" was therefore wrong for custom widths (ordinary `OX-win`, 910mm, O=500/X=510: exported 450) and for unequal `X` widths (only the first `X` was read). The real width of the remainder-side leaf is not recoverable from the tree at all, so `buildSlidingWinOverlapTree` now stamps each section node with `panelWidthMM` = its entered width. Fresh creation and "Edit assembly widths" both go through that builder, so a reopen always re-stamps with the newly entered widths. The builder shallow-copies the section nodes rather than mutating them, so an edit rejected by the size check leaves the live tree untouched. Export reads `panelWidthMM`. The reopen form prefills from it too; it used to read drawn widths, so a reopened `O` showed its tuck-in-reduced width. The `xMM` rule above is unchanged, just fed the stored widths: the rightmost panel's right edge still lands at `openingW + tuckIn/2`, because entered widths always satisfy the total check. Changing a section's type carries `panelWidthMM` over (the panel's made size doesn't depend on its type). The field is all-or-nothing per assembly: if any section lacks it (a `rawState` saved before batch 49), the whole assembly falls back to batch 48's reconstruction for both export and reopen. `rawStateSchemaVersion` is not bumped, because a missing field is handled.

**Batch 51 — subdivided sections: construction assumption, storage moved to the marker, and the per-section correction.**

*The problem batch 49 left open.* Users regularly subdivide a sliding section further — a transom across it, or a vertical bar splitting it into two panes side by side, at any nesting depth. Splitting a section replaces its tree node (`cloneForSplit` builds the two new children, carrying neither `panelWidthMM` nor `sashless`), so batch 49's per-section stamp had nowhere to survive: the export correction's own leaf-count check (`assemblyLeaves.length !== n`) then silently found more leaves than the pattern had letters and bailed out with **no correction and no warning** — the whole row exported its raw, tuck-in-absorbed drawn widths. Reopen had the matching failure: no `panelWidthMM` on the (now-split) section node meant it fell back to batch 48's reconstruction, wrong for any custom width.

*Person-confirmed construction assumption.* A subdivided sliding section is still **one physical panel** — one sash that slides or stays fixed as a single unit, with a glazing bar or transom inside it, not two independent panels that happen to sit side by side. The hidden strips at a panel's own perimeter — the frame tuck-in on an outer edge, the sliding overlap running behind a neighbouring panel — belong to whichever sub-pane actually sits on that perimeter edge, not to the section as an undifferentiated whole.

*Stated interpretation — the person has been told the consequence.* A bar's position inside a panel is taken as its **true position in the opening, exactly as drawn** — it is never re-measured along the panel's own real (corrected) width. The practical result: splitting a panel at its own drawn centre does NOT generally produce two equal real panes. Worked example, ordinary `OX` (door), 910mm opening, framed, O=500mm/X=510mm entered: the drawn `X` spans local [400,910] (510mm, already equal to its real width — batch 48's own finding). Splitting it with a 40mm bar at its own drawn centre (local 655) puts the bar at local [635,675], leaving drawn sub-panes [400,635] (235mm) and [675,910] (235mm). But the `X` section's own two perimeter strips aren't equal — its left edge absorbs a −20mm correction (the real assembly x-origin sits 20mm to the RIGHT of where `X`'s drawn geometry starts, because of how the overlap join places it) and its right edge absorbs +20mm (from the row's own frame tuck-in) — so the real, exported sub-panes come out **215mm and 255mm**, unequal, even though the bar sits exactly at the section's own drawn centre. `215 + 40 (bar) + 255 = 510`, the entered width, exactly. This is the drawing's existing tuck-in/overlap absorption showing through one side of the split rather than the other — not corrected for, per the stated interpretation above.

*Storage.* Moved from the per-section node stamp (batch 49) to the assembly's own marker: `assemblyPresetRef` on the row's top-level tree node now carries `panelWidthsMM`, an array of the entered section widths in pattern order, alongside the existing `pattern`/`productClass`/`id`. Stamped fresh on `confirmAssemblyPreset`; replaced with a freshly-built array (never mutated in place) on every `confirmAssemblyEdit`, so a validation-rejected reopen leaves the live marker untouched. A split, a Clear, or a type change never touches the marker node at all, so a subdivided section's real width now survives all three automatically — nothing to re-stamp, because nothing holding the width was ever disturbed.

*The correction, now per SECTION rather than per leaf.* For each section (a full letter of the pattern — one leaf if never subdivided, an entire subtree if it has been): its own drawn rect (x, width) comes from a node-rect map recorded for every node the export traversal visits, keyed by that node's own tree path — this works identically whether the section is a leaf or a split, since the map doesn't care which. The row-level x/width placement rule from batch 48/49 is otherwise unchanged, just driven by section rects instead of leaf rects: section 0 starts `tuckIn/2` left of its own drawn x; each next section is placed from its left neighbour's real end, minus `SLIDING_OVERLAP_MM` at an overlap join or 0 at a flush join (read directly off the sections' own drawn adjacency, same as before). Per section, `leftStrip = drawnX − realX` and `rightStrip = (realX+realW) − (drawnX+drawnW)` — either can be negative, never clamped (the `X` example above has `leftStrip = −20`). Every exported leaf whose own path falls under a section's path is then corrected using THAT section's own strips: a leaf touching the section's drawn left edge absorbs `leftStrip`, one touching the drawn right edge absorbs `rightStrip`, one touching both (unsplit, or either side of a transom split — a horizontal split doesn't move either child off the section's own left/right edges) absorbs both, and one touching neither (fully interior) is left exactly as drawn.

*Never silently wrong.* If a section's own path doesn't resolve to a rect at all (the tree and the section-path computation disagreeing, which should never happen — the paths are the same ones `buildSlidingWinOverlapTree`'s own construction produces, cross-checked since batch 17/18), the export throws rather than silently repeating batch 49's "leaf count doesn't match, skip the correction" failure mode. This surfaces as an uncaught exception from the Export/Done button's own click handler in either mode (standalone or embedded) — nothing in this file wraps `buildExportData` in a try/catch — no different in kind from any other uncaught throw already possible in this codebase (`classifySlidingWinJoin`'s own throws, for one).

*Unaffected.* `unframedEdgeCount`, `unframedEdges` (including Case 4's own x-range overlap test), meeting-jamb touch detection, and the cross-elevation pane link all keep running on the ORIGINAL drawn geometry — confirmed unchanged for every case tested. The sashless tuck-in check is unchanged (still keys off whether any of the assembly's own leaves carry `sashless: true`) — a **subdivided sashless panel's own widths are known-wrong until a future batch** revisits how a sashless row's tuck-in should distribute across a split panel; this batch only needed it not to crash, which it doesn't.

## Real vertical (head/sill) panel size for sliding-window/door assemblies (batch 57, `fixed`-pane exemption corrected batch 58)

**Closes the "batch 48, open gap" note above.** Person-confirmed (Duce): a framed, non-sashless sliding-window/door row's panel also tucks in vertically — 20mm into the head + 20mm into the sill, `SLIDING_HEIGHT_TUCKIN_MM = 40`. This is a separate, dedicated constant from `FRAME_TUCKIN_MM`, not a reuse of it, even though the two values happen to match — same precedent as `PANE_EDGE_MATCH_TOL_MM` being kept separate from `EDGE_TOUCH_EPS_MM` despite the two being built for unrelated reasons. The match is a coincidence (both are "20mm per frame-touching edge, 2 edges"); a future change to either figure must not be assumed to apply to the other.

**No per-section fold on this axis.** The width correction above exists because the row's own horizontal frame tuck-in gets folded unevenly across sections by `buildSlidingWinOverlapTree`'s internal overlap-join mechanics — there is no equivalent vertical folding anywhere in the tree (a sliding assembly's sections sit side by side along one axis only). So the vertical correction needs only the marked row's own single drawn rect — `nodeRects[pathKey(markedPath)]` — never a per-section rect the way the width correction does. That rect is correct even when the row itself is nested inside a vertically-subdivided parent (a rare but tree-legal case): `collectExportGeometry`'s own recursion always passes accumulated, absolute x/y down through every split (confirmed by reading its body directly, not assumed), so `nodeRects` entries are absolute-in-elevation coordinates regardless of nesting depth or axis.

**Binary, not three-way.** Unlike the width correction's `FRAME_TUCKIN_MM`/`SASHLESS_FRAME_TUCKIN_MM`/`0` three-way choice, the vertical tuck-in is person-confirmed binary: `0` or `SLIDING_HEIGHT_TUCKIN_MM`, with no smaller nonzero figure for a sashless row (sashless is computed the same way as the width correction — true if any leaf in the marked assembly carries `sashless: true`).

**Mechanism.** New `computeSlidingAssemblyVerticalCorrections(leaves, ev, nodeRects)`, alongside `computeSlidingAssemblyLeafCorrections`, reusing the same `collectSlidingAssemblyRanges` (sliding-window/door only, `isSlidingOverlapId`-gated — confirmed that double-hung's own `'D'`/`'DD'`/`'DDD'` patterns never match that regex, so double-hung's own vertical tuck-in remains a separate, still-open item). For each range: `tuckInV = (ev.hasFrame && !sashless) ? SLIDING_HEIGHT_TUCKIN_MM : 0`; `topStrip = bottomStrip = tuckInV / 2`.

**Per-leaf gate (batch 58), NOT row-uniform.** Batch 57's first version applied `tuckInV` to every leaf in the range that touched the row's own drawn top/bottom edge — including a `fixed` (`O`) leaf, which has no sash at all. Person-confirmed (Duce): a fixed pane has no sash mechanism to tuck into a head/sill track, so it must always report its height flush with the drawn opening geometry, in both the sashless and ordinary case — this bug showed up concretely as an ordinary `OX-win`'s `O` exporting `heightMM: 1040` in a 1000mm-high opening, when it should stay `1000`. Fixed by checking `l.node.type === 'fixed'` FIRST, per leaf, before the touch tests: a fixed leaf always gets `{y: l.y, h: l.h}` — identity, full stop, regardless of `tuckInV`, `hasFrame`, or `sashless`. Only a real sash leaf (non-`fixed`, i.e. the sliding `X`) ever absorbs `topStrip`/`bottomStrip`, using the same touch-tested absorption rule the width correction uses on x (`touchesTop`/`touchesBottom` against the row rect, within `EDGE_TOUCH_EPS_MM`). **This is a genuine, deliberate divergence from the width/jamb correction** (`computeSlidingAssemblyLeafCorrections`), which does NOT exempt `O` — `O` legitimately absorbs jamb tuck-in for WIDTH (batch 48's own worked example: `O` drawn 435mm, real 475mm) — confirmed by diff that batch 58 touches only `computeSlidingAssemblyVerticalCorrections`, not the width function.

Returns a read-only `Map` (leaf → `{y, h}`), wired into `buildExportElevation` as `verticalCorrections`, used for `heightMM`, `yMM` (via the corrected `y+h`), `areaM2`, `visibleGlazedAreaM2`, and `frameLengthMM`'s sash-perimeter term — the same five fields the width correction feeds, just the height/y side of each. Since `frameLengthMM`'s sash-perimeter term only sums non-`fixed` panes in the first place (see "Frame length calculation" below), the `O` exemption here has no separate effect on that total beyond `O` simply never contributing a sash perimeter at all, same as before.

**Unaffected, confirmed by diff.** `unframedEdgeCount`, `unframedEdges` (including Case 4), `unframedEdgeReasons`, meeting-jamb touch detection, `computeCrossElevationLinks`, and the existing `widthMM`/`xMM` correction all keep reading `l.y`/`l.h`/`l.x`/`l.w` or their own existing logic directly — none of them read `verticalCorrections`.

No `schemaVersion` bump, for either batch — this fills an already-documented open gap in the existing v5 shape and then corrects a bug within that same fill, not a new field, same precedent batch 48 set for the width fix.

## Real jamb (widthMM/xMM) panel size for double-hung units (batch 59)

**A previously-undocumented gap, not a flagged one — found and closed in the same batch.** Person-confirmed (Duce): a framed double-hung unit's panel also tucks into its own left/right side by 20mm each (40mm total), the same physical idea as the sliding-window/door jamb tuck-in (`computeSlidingAssemblyLeafCorrections`, batch 48) — but a different constant and a different shape. New `DOUBLE_HUNG_JAMB_TUCKIN_MM = 40`, deliberately a SEPARATE constant from `FRAME_TUCKIN_MM`, not a reuse — same precedent as `SLIDING_HEIGHT_TUCKIN_MM` and `PANE_EDGE_MATCH_TOL_MM`/`EDGE_TOUCH_EPS_MM` before it — even though double-hung's own VERTICAL overlap (`getDoubleHungOverlapMM`) already legitimately reuses `FRAME_TUCKIN_MM` directly, for the meeting-rail overlap's own tuck-in term, on a different axis entirely; that function is untouched by this batch.

**Per UNIT, not per row — the key structural difference from every prior tuck-in correction in this file.** A sliding-window/door row is corrected once for the whole row (width) or once for the whole row (height, batch 57/58); a double-hung row's units are structurally independent panels sitting side by side, each with its own left/right tuck-in, regardless of what's next to it — a true outer jamb on one side, or just an ordinary mullion shared with the neighbouring unit on the other. **A middle unit in a `DDD` row (a mullion on BOTH sides, no true jamb touching it at all) still gets the FULL 40mm, not zero** — each unit is corrected against its own drawn rect independently, never against the whole assembly's outer rect the way the sliding-row width correction is.

**Marked-tree detection.** Reuses the existing `detectPresetFamily(ref.pattern) === 'double-hung'` check (already confirmed globally unique against every other family's pattern strings, batch 14) via a new `collectDoubleHungAssemblyRanges`, structured exactly like `collectSlidingAssemblyRanges` (batch 48) but gated on this check instead of `isSlidingOverlapId`, and additionally carrying the matched node itself (not just its path), since finding each unit's own path needs to walk that subtree directly.

**Unit-boundary detection.** New `collectDoubleHungUnitPaths(node, path, out)` walks a double-hung marked tree structurally rather than hand-deriving `foldSectionsIntoSplits`' own fold order: `kind: 'sashSplit'` means the node IS one whole unit (`buildDoubleHungUnit`'s own top/bottom vertical-slider pair) — pushed, not recursed into further; `kind: 'split'` is `foldSectionsIntoSplits`' own real mullion wrapping two units (or a unit and a further-nested split, for `DDD`) — recursed into on both sides. This stays correct even if `foldSectionsIntoSplits`' own shape changes later, the same reasoning batch 51 used for sliding section paths instead of hand-counting leaves.

**Mechanism.** New `computeDoubleHungWidthCorrections(leaves, ev, nodeRects)`. For each double-hung marked tree found: `sashless = assemblyLeaves.some(l => l.node.sashless === true)` — confirmed all-or-nothing across a double-hung preset (batch 42, one checkbox, no per-unit choice), but still checked via `.some()` rather than assumed true without looking, same discipline the vertical correction (batch 57) already applies to its own sashless check. `tuckInH = (ev.hasFrame && !sashless) ? DOUBLE_HUNG_JAMB_TUCKIN_MM : 0`; `leftStrip = rightStrip = tuckInH / 2`. For each unit path found via `collectDoubleHungUnitPaths`: `unitRect = nodeRects[pathKey(markedPath.concat(unitPath))]` — the UNIT's own drawn rect (not the assembly's whole-row rect, unlike the sliding-row corrections). For every leaf under that unit's path — both the top and bottom sash, which share the same x/w since the unit's own `sashSplit` only varies y — `touchesLeft`/`touchesRight` are tested against the UNIT's own rect. Since a unit's top/bottom leaves always span the unit's own full drawn width (a `sashSplit` on axis `'h'` passes x/w through unchanged to both children — confirmed by reading `collectExportGeometry`'s own `sashSplit` branch directly), both leaves always touch both of their unit's own left/right edges, so both always absorb the FULL `leftStrip + rightStrip` together — which is exactly what makes every unit's correction independent of its neighbours, and exactly what gives a `DDD` middle unit its full 40mm despite having no true outer jamb.

Returns a read-only `Map` (leaf → `{x, w}`), wired into `buildExportElevation` as `doubleHungCorrections`, a second fallback after `slidingCorrections`: `realGeom = slidingCorrections.get(l) || doubleHungCorrections.get(l) || { x: l.x, w: l.w }`. The two maps never have an entry for the same leaf — sliding-window/door and double-hung are mutually exclusive preset families (a leaf belongs to at most one assembly-preset marker) — so this fallback chain is safe. Feeds the same five fields the sliding jamb correction feeds: `widthMM`, `xMM`, `areaM2`, `visibleGlazedAreaM2`, and `frameLengthMM`'s sash-perimeter term.

**Unaffected, confirmed by diff.** `getDoubleHungOverlapMM`/`DOUBLE_HUNG_OVERLAP_MM` (a different axis, already correct), `heightMM`/`yMM` for a double-hung pane (already correct — this batch is width/jamb only), `unframedEdgeCount`, `unframedEdges`, `unframedEdgeReasons`, meeting-jamb touch detection, and `computeCrossElevationLinks` all keep reading the original drawn geometry or their own existing logic directly.

No `schemaVersion` bump — this fills a previously-undocumented gap in the existing v5 shape (`widthMM`/`xMM` were always silently wrong for a framed double-hung unit, never flagged as an open item the way the sliding-panel-height gap was), not a new field — same precedent batch 48 set.

## Lone and manually split slider tuck-in (batch 60)

**Scope.** `computeLoneSlidingLeafCorrections(leaves, ev, openingW, openingH)` corrects any `horizontal-slider` or `vertical-slider` leaf that is NOT under an `assemblyPresetRef` marker (checked against the exact same ranges `collectSlidingAssemblyRanges`/`collectDoubleHungAssemblyRanges` collect for the separate preset pipeline — a leaf under a preset is skipped entirely and always corrected by that other pipeline instead, never by this one). This covers two kinds of leaf: a single slider typed directly via the per-pane dropdown, filling the whole opening; and either side of a slider pair built with the mullion/split tool by hand (not any OX/OXX/OXXO or D/DD/DDD preset).

**Spans two commits, written up as one batch.** `dad98aa` ("Add tuck-in correction for a lone (non-preset) sliding leaf on export") added this function, gated on a leaf touching all four opening edges — a manually split leaf, touching fewer than four, got no correction at all. `24f1e45` ("Rewrite lone-sliding-leaf tuck-in to test each edge independently") replaced that whole-leaf gate with the per-edge rule below. Neither commit had a batch number at the time; both are batch 60.

**Per-edge rule.** Each of a leaf's 4 edges is tested independently, not as a single all-or-nothing leaf test:

- An edge touching the **outer frame** (jamb, head, or sill) gets `tuckIn/2`.
- An edge touching a **real sibling mullion** — the nearest ancestor split of the matching axis (found by a new `findAdjacentSplit(root, path, axis, side)` helper, which walks DOWN from the tree root along the leaf's own path so the deepest/nearest qualifying split wins, never an outer split several levels further up) with `thicknessMM > 0` and not `isSiliconeJoint` — also gets `tuckIn/2`, the identical magnitude as an outer-frame edge.
- A **flush (zero-thickness) split**, a **silicone joint**, or an edge that's **interior to a further subdivision** (no ancestor split of the matching axis touches that side at all) gets no correction.

Left/right tuck-in uses `FRAME_TUCKIN_MM`, halved to `SASHLESS_FRAME_TUCKIN_MM` when the leaf's own `sashless === true`, zero when `ev.hasFrame` is false. Mullion tuck-in (left/right) is tested and applied identically for `horizontal-slider` and `vertical-slider` leaves — a mullion is a vertical divider regardless of which way the leaf itself slides.

**Top/bottom is not slider-type-gated, but it IS frame-only — read this before assuming otherwise.** Top/bottom tuck-in (`SLIDING_HEIGHT_TUCKIN_MM`, halved per edge) is applied whenever the leaf's top or bottom edge touches the **outer frame**, forced to 0 when sashless, and zero when `ev.hasFrame` is false — with **no check on `node.type` at all**. A `vertical-slider` leaf gets exactly the same top/bottom tuck-in a `horizontal-slider` leaf gets, when that edge touches the frame. This has been true since `dad98aa` and is unchanged by `24f1e45`. **The rule is asymmetric between axes: `findAdjacentSplit` is only ever called with axis `'v'` — there is no equivalent real-mullion lookup for the top/bottom (`'h'`) axis at all, for either slider type.** A leaf's top/bottom edge touching a real horizontal mullion gets NO tuck-in there, only the frame-touching edge does (confirmed directly by reading the function: `tuckTop`/`tuckBottom` are set solely from `touchesFrameTop`/`touchesFrameBottom`, never from an `isRealMullion` check on that axis). Summarized: **left/right edges — frame or a real mullion (`thicknessMM > 0`) gets `tuckIn/2`; top/bottom edges — frame only, no correction at a horizontal mullion.** **The AS 1288 side has confirmed that a lone vertical slider genuinely does tuck into its head and sill** — the mechanism is real — **but the specific 20mm-per-end amount applied here is `SLIDING_HEIGHT_TUCKIN_MM`, the horizontal slider's own confirmed figure, reused for vertical sliders without a separate confirmation that 20mm/end is the correct amount for a vertical slider's own head/sill track. Top/bottom tuck-in at a real horizontal mullion is unconfirmed and not implemented.** Do not change `SLIDING_HEIGHT_TUCKIN_MM`'s value, and do not add a horizontal-mullion tuck-in rule, until confirmed — see `Configurator_Project_Summary.md` §5's open items.

**No entry at all, not a zero-valued one.** If none of a leaf's 4 edges qualify for any correction, the function returns without adding that leaf to its correction map (no `corrections.set(l, ...)` call) — there is no map entry, not an entry holding all-zero deltas. This happens for more than just the manually-split case: it also happens whenever `ev.hasFrame` is false (every tuck-in constant resolves to 0 regardless of touch), and for a leaf every one of whose edges is either a flush split or interior to a further subdivision with no frame touch at all.

**Confirmed unaffected, on purpose.** Preset `OXXO`'s own middle X-X join is photo-confirmed genuinely flush (no mullion) — its existing zero-correction there is untouched. Preset `DD`/`DDD` already gets full 40mm tuck-in at its own internal mullion joins (batch 59) — also untouched. Both are reached through the completely separate, `assemblyPresetRef`-gated pipeline this function skips via its own `assemblyRanges.some(...)` guard.

**Worked example**, real output from the current code — 1800×2100mm overall, 60mm frame members (opening 1680×1980), two `horizontal-slider` leaves with 40mm sash edges, split by a manual 50mm-thick vertical mullion at the opening's centre (not a preset):

```json
[
  { "type": "horizontal-slider", "xMM": 40,  "yMM": 40, "widthMM": 855, "heightMM": 2020 },
  { "type": "horizontal-slider", "xMM": 905, "yMM": 40, "widthMM": 855, "heightMM": 2020 }
]
```

Each raw drawn leaf is 815mm wide ((1680 − 50) / 2). Each leaf's outer-jamb edge and its mullion-facing edge both qualify (real 50mm mullion, not flush) and each gets `FRAME_TUCKIN_MM/2 = 20mm`, so each leaf's width grows by 40mm to 855mm; the left leaf's `x` shifts left by 20mm (drawn 0 → −20, plus `jambL` 60mm → `xMM` 40), the right leaf's `x` shifts left by 20mm too (drawn 865 → 845, plus `jambL` 60mm → `xMM` 905). Both leaves get `yMM:40`/`heightMM:2020` — the full outer-frame top/bottom tuck-in, since both edges touch the opening's own head/sill (unaffected by the vertical split).

A second real trace, two `vertical-slider` leaves split by a manual 50mm-thick **horizontal** bar (same 1800×2100/60mm-frame elevation; `yMM` is measured from the bottom of the opening, Y up): bottom leaf `{xMM:40, yMM:40, widthMM:1720, heightMM:985}`, top leaf `{xMM:40, yMM:1075, widthMM:1720, heightMM:985}` — both leaves' left/right edges get the full outer-jamb tuck-in (no vertical split there; each is 1720mm, the full opening width plus 40mm). Each leaf's own FRAME-facing top/bottom edge gets `SLIDING_HEIGHT_TUCKIN_MM/2 = 20mm` — the bottom leaf's bottom edge, the top leaf's top edge — but **the bar-facing edge of each leaf gets NO tuck-in at all**: each leaf's raw drawn height is 965mm ((1980 − 50) / 2), and each corrected height is 985mm, i.e. only 20mm was added, on the one frame-facing edge, not 40mm split across both. The 50mm gap between the two leaves' drawn rects is untouched — confirming `computeLoneSlidingLeafCorrections` has no real-mullion rule on the top/bottom axis at all (see below), for either slider type.

A third real trace, `fixed` + `vertical-slider` split by the same manual mullion tool (real 50mm-thick vertical bar): the `fixed` leaf exports flush at its own drawn geometry on every edge (`{xMM:60, yMM:60, widthMM:815, heightMM:1980}` — no correction at all, `fixed` is out of scope for this function entirely, `node.type` check at the top excludes it), while the neighbouring `vertical-slider` leaf gets full jamb-and-mullion tuck-in exactly as in the two-slider case.

## Stale `panelWidthsMM` detection and self-healing reopen (batch 52, per-section detection batch 53)

Batch 51 identified two on-drawing edit paths that can change a sliding assembly's real section widths **without going through "Confirm resize" (`confirmAssemblyEdit`) at all**, which is the only place `panelWidthsMM` gets re-stamped — leaving the marker's stored widths describing a shape that no longer matches the row's own real geometry:

1. Growing or shrinking the elevation's overall width/height (its own on-drawing double-click label, or the header's plain Overall width/height inputs).
2. Double-clicking a plain-split bar's own on-drawing dimension label — a manually-added bar inside a subdivided section, or (for `OXXO`) the assembly's own internal zero-thickness flush-join split.

At the time, nothing detected either case — export silently used the stale marker. Batch 52 built detection and a self-healing reopen; its own first version, a whole-row TOTAL comparison, could only catch edit path 1. Batch 53 replaced it with a per-SECTION comparison that catches both.

**Why the row-total version (batch 52) wasn't enough.** `computeSlidingAssemblyLeafCorrections` compared `computeSlidingWinTotalWidth(ref.pattern, ref.panelWidthsMM, sashless)` (what the marker's stored widths claim the row's real total is) against the row's own outer drawn span (first section's left edge to last section's right edge). This DOES catch edit path 1 — growing or shrinking the row genuinely changes its own outer total. It does NOT catch edit path 2, and this isn't a near-miss: `OXXO`'s own inter-run joining split is always built with `thicknessMM:0`, and for a zero-thickness split, its two sides' widths always sum to exactly the outer container width for ANY `posMM` (`leftW = posMM`, `rightW = w − posMM`, `leftW + rightW = w` always). Moving the bar redistributes space between the two runs but provably cannot change the row's own outer total — confirmed directly, not just algebraically: moved a real `OXXO`'s flush bar from `posMM` 1190 to 1340 and the marked node's own rect stayed exactly 2400mm wide, unchanged; the row-total check saw nothing to flag.

**The fix (batch 53): compare each section against a snapshot of itself, not the row against its own total.** A new marker field, `sectionDrawnWidthsMM`, records each section's own DRAWN width (not its real/entered width — `panelWidthsMM` already has that; the section's own drawn width, which differs from real by whatever tuck-in/overlap strip lands on it), in pattern order, as actually rendered at the moment `panelWidthsMM` was last stamped. Both `confirmAssemblyPreset` and `confirmAssemblyEdit` capture it immediately after their own `render()` call (the drawn geometry only exists once the freshly-built/resized tree has actually been walked), writing it onto the marker object already living in the committed tree — no second `render()`, pure bookkeeping alongside the marker's other fields. `isPanelWidthsStale(ref, sectionRects, sashless)` now compares each `sectionRects[i].w` against `ref.sectionDrawnWidthsMM[i]` directly; stale if ANY section differs by more than 0.01mm. This catches edit path 2 because moving the flush-join bar DOES change the drawn width of whichever sections sit on either side of it (their own allocated run grows or shrinks), even though the row's outer total doesn't move — no analytical re-derivation needed, just a direct before/after comparison per section.

`sashless` is kept as a parameter (both call sites still pass it, unchanged) but is no longer read by the comparison itself — a direct per-section width diff needs no tuck-in knowledge, unlike the old total-based formula.

**Both edit paths are now caught.** Export's throw names exactly which section(s) changed and their before/after widths — e.g. for the `OXXO` flush-bar case, `section 0 (O): was 610mm, now drawn at 760mm; section 3 (O): was 570mm, now drawn at 420mm` (precisely the two sections either side of the moved join; the two untouched sections, 1 and 2, aren't mentioned). A bar moved strictly INSIDE one already-subdivided section (not between pattern-letter sections) is still correctly never flagged — that section's own outer span, and therefore its own drawn width as a whole, is unchanged; only its internal split moved, exactly the harmless case batch 51 already handles via its own leftStrip/rightStrip mechanism.

**A marker with `panelWidthsMM` but no `sectionDrawnWidthsMM`** — a `rawState` saved between batch 51 and batch 53, after storage moved to the marker but before this snapshot existed — is treated exactly like `panelWidthsMM` being absent for STALENESS-CHECKING purposes only: `isPanelWidthsStale` returns `false` (can't tell without a snapshot, so it doesn't guess), no throw. This is NOT the same as falling back to batch 48's X-based reconstruction: `resolveSlidingRealWidths` (unchanged by this batch) still finds `panelWidthsMM` present and valid and uses it directly, exactly as batch 51/52 already did for such a marker. Batch 48's reconstruction remains reserved for the genuinely older case — no `panelWidthsMM` at all (pre-batch-49).

**Reopen (self-healing) needed no further changes.** `getAssemblyPresetCurrentState`'s own batch-52 prefill logic — current drawn widths, with the row's own tuck-in added to `pattern.lastIndexOf('O')`, the one section whose entered value never affects rendered geometry — only ever depended on `isPanelWidthsStale`'s boolean result, not on how it was computed. Confirmed by tracing, not assumed: the underlying math (the sum constraint is satisfied algebraically regardless of which section absorbs the tuck-in; the last run's own `O` is always the one dynamically-computed section) holds whether the staleness was caused by an overall resize or by a redistributed run. Verified directly: reopening a bar-moved `OXXO` prefills `[760, 640, 700, 460]` (all four sections' own current drawn widths, with the row's full 40mm tuck-in added to section 3) and confirming unchanged both passes the total check and reproduces the row's exact new geometry.

(Batch 52's own reopen-side fix — `renderAssemblyPresetForm`'s edit-mode `availableWidth` reading the marked node's own live drawn width directly, instead of the prefill's own total — is unchanged and still required; without it "Confirm resize" would still be validating against a number derived from whatever's in the input boxes, defeating the point of showing the person the real current state.)

## `rawState` — raw internal state block (batch 37)

A second, separate top-level field, sitting alongside `system`, not inside it. Where `system` is a deliberately simplified, derived flat pane list (§'s own core principle above — the tree is "editing-session bookkeeping" that "nobody downstream needs to know"), `rawState` is the opposite: the configurator's actual live internal state, sufficient to fully reconstruct an editing session later (preset refs, hinged-door refs, sash locks, meeting edges, the split tree itself — everything `system` deliberately discards).

**`rawState` is explicitly opaque to any consumer.** The AS 1288 tool (or any other reader) stores and returns it unread — it never parses or derives anything from `rawState`'s own contents. This is why `schemaVersion` does not cover it: `schemaVersion` versions `system`'s own derived shape only. `rawState`'s own internal shape can change freely between configurator versions without being a breaking change for any consumer, precisely because no consumer is expected to read it — it only round-trips through whatever external system stores it, until the configurator itself (via `restoreFromRawState()`) reads it back.

Produced by `serializeRawState()`, consumed by `restoreFromRawState()` — both in `configurator_prototype_oxxo_8.html`. Shape, as of batch 38:

```json
{
  "rawStateSchemaVersion": 1,
  "elevations": [ /* the full live elevation objects — tree, overallW/overallH, hasFrame,
                     frameMembers, meetingEdges, meetingLink, selected, pendingSplit, etc. —
                     not a derived form, the actual internal representation */ ],
  "activeElevationIndex": 0,
  "angledJoinAngleDeg": null,
  "angledJoinType": null
}
```

**`rawStateSchemaVersion` (added batch 38).** Batch 37 deliberately left `rawState` unversioned, since it's opaque to the AS 1288 tool and nothing external was expected to read it. Batch 38's embed-mode "load" handshake changed that: the CONFIGURATOR ITSELF now needs to recognize its own state shape before trusting a `rawState` blob handed back to it on load — so a minimal version marker was added specifically to give that check something real to validate against, rather than skipping it. This is a small, deliberate scope addition beyond what batch 37 shipped, flagged here rather than folded in silently. It has no relationship to `schemaVersion` (which still only describes `system`'s own derived shape) — bump `rawStateSchemaVersion` only when `restoreFromRawState()`'s expectations of what `serializeRawState()` produces change in an incompatible way.

`restoreFromRawState()` is now wired into the embed-mode "load" message (see "postMessage embed protocol" below) — no longer prerequisite-only as of batch 38.

## postMessage embed protocol (batch 38)

When this configurator is opened inside an `<iframe>` (`window.parent !== window`), it runs a same-origin postMessage handshake with the parent page instead of behaving as a standalone tool. **Standalone mode (opened directly, not embedded) is completely unaffected** — no listener is ever registered, and "Export JSON" keeps downloading a file exactly as before.

**Security — same-origin only, no hardcoded URL:**
- Every message this configurator SENDS targets `window.parent` with `window.location.origin` as the explicit target origin — never `'*'`.
- Every message this configurator RECEIVES is checked against BOTH `event.origin === window.location.origin` AND `event.source === window.parent` before anything in it is read. Failing either check is a silent drop — no error, no console output, no partial processing.

**Handshake, in order:**

1. **`ready`** — sent by the configurator once its own initial render has genuinely finished (not before): `{ "type": "ready", "schemaVersion": 6 }`. `schemaVersion` here is the export's own `system` schema version (v1 → v2 in batch 39, v2 → v3 in batch 43, v3 → v4 in batch 44, v4 → v5 in batch 55, v5 → v6 in batch 61) — this tells the parent which derived-pane-list shape/meaning a subsequent `done` will use, and it always matches `done`'s own `export.schemaVersion`. The v5→v6 bump is unusual versus every prior bump: no field was added — `unframedEdges`/`unframedEdgeReasons` gained a new possible value (Case 5, `'sashless-free-edge'`) and the old sashless top/bottom exception was removed, so an existing consumer reading those two fields against a sashless pane would see different values under the identical shape. See the "Sashless free-edge flag (Case 5, batch 61)" section above.
2. **`load`** — sent by the parent in response, exactly once: `{ "type": "load", "state": null | <a previously-saved rawState blob> }`.
   - `state: null` — start a fresh, single-elevation session (the existing default). `restoreFromRawState()` is never called.
   - `state: { ...a real rawState object... }` — its own `rawStateSchemaVersion` is checked first. If it doesn't match the configurator's own `RAW_STATE_SCHEMA_VERSION`, the configurator shows a persistent, visible in-page error (not a console log, not an `alert()`) and stops — `restoreFromRawState()` is never called, no partial or best-effort load is attempted. If it matches, `restoreFromRawState(state)` runs and the session is fully reconstructed.
3. The user edits normally — nothing about the editing UI differs in embed mode.
4. **`done`** — sent by the configurator when the user finishes: `{ "type": "done", "export": <the full buildExportData() output, i.e. { schemaVersion, system, rawState }> }`. This is the ONLY way `done` ever fires. It's driven by the same "Export JSON" button, relabelled "Done" in embed mode — one button, one conditional action, rather than a second embed-only control. In embed mode this button sends the postMessage instead of downloading a file.

**No cancel/close from the configurator.** Per the agreed protocol, cancel/close belongs entirely to the parent page's own modal chrome (its own close button). The configurator renders no close/cancel control in any mode and never sends a cancel-type message — only `ready` and `done` are ever constructed.

**No row/system ID handling.** The parent tracks which schedule row is open; the configurator neither accepts, stores, nor echoes back any kind of identifier.
