## 1. What this is and why it exists
 
A standalone, browser-based configurator for building up a window/door elevation: an opening, an optional outer frame, and a recursively-divided grid of panes, each assignable a type and a door/window classification. Every dimension is shown directly on the drawing and is editable there.
 
It grew out of, but stays deliberately separate from, the AS 1288 Glass Thickness Calculator project at Duce Timber Windows and Doors. It's explicitly not a calculator-specific feature — the intent is a standalone tool other tools can consume: the AS 1288 compliance engine (needs per-pane span, aspect ratio, framing condition), and a future pricing/quoting tool (needs per-pane glass area, frame linear lengths, counts). **This intent is no longer purely aspirational — §6.7 below records an actual, specific plan for the AS 1288 side of this, decided in a recent session, not yet built.**
 
Open strategic question, still unresolved, worth raising again before real investment: Duce has a Logikal vendor evaluation in progress (a commercial fenestration ERP with its own parametric configurator and quoting), and a separate parked Fusion 360 drawing-handoff initiative. Building this configurator in-house may duplicate either. This question resurfaced when discussing a genuine 3D parametric model (see §8) — the same duplication risk applies there, at a much larger scale, and was a deciding factor in choosing a data-only approach over a 3D rendering approach for depth/z-axis capture.
 
Current state of the actual artifact: a single self-contained HTML file (`configurator_prototype_oxxo_8.html`), vanilla JS, no frameworks or build step, **no backend, no persistence — this is a deliberate, standing architectural boundary, not just a current limitation (see §6.7 on why storage stays out of this file even as the AS 1288 integration takes shape).** Nothing is wired into the AS 1288 Flask app yet, though the integration architecture is decided (§6) and one standalone piece of it has been built and tested (§6.4) **elsewhere** — not in this repo (see §9's note on environment gaps). Built entirely inside Claude chat sessions and Claude Code sessions, iterated batch by batch.
 
**This project lives in its own claude.ai Project, with no visibility into the AS 1288 Tool project (a separate Project).** A chat session bound to this Configurator Project cannot read or list files belonging to that other Project. When work here needs to hand off to that side, the practical approach confirmed in this session is: bring the current version of this document, the actual `configurator_prototype_oxxo_8.html` file, and `side_panel_rule_tester.html` (§6.4) into a chat under the AS 1288 Tool Project directly, and let that session reconcile against whatever it already independently knows — don't assume alignment from this side.
 
**Important scope clarification, worth stating plainly because it was briefly gotten wrong mid-session (see §11):** "the configurator works on one system at a time" means it doesn't hold a *list* of many different schedule items open simultaneously — that list-holding job belongs to the AS 1288 tool. It does **not** mean a single system is capped at one elevation. If one system (one AS 1288 schedule item) genuinely has two linked elevations — the angled-joint case, §7.4 — the configurator itself is the tool responsible for holding and editing both together, in one working session, once that feature exists.
 
## 2. Data model (current state, post-batch-24; §7.4's proposed additions not yet built)
 
### 2.1 — The two-level concept this sits inside (upstream context — no longer just a someday-idea, but still not built)
 
The broader "window schedule" concept this configurator serves is two levels: Opening (a schedule row/job line item) and System(s) (one or more glazed units within that opening). **A single system can itself have more than one elevation** (confirmed in §7.4 — the angled-joint case is exactly this: one system, two linked elevations). A two-elevation *state model* was built in batch 25 (`elevations[]` array, `setActiveElevationIndex`, `renderElevationTabs`) with a temporary, uncapped "+ Add elevation" placeholder button. **Batch 26 replaced that placeholder with the real trigger:** "Add angled join" is now the only way to create a second elevation — it asks which jamb (left/right only; head/sill not yet exposed) is the meeting edge, blocks the action if existing panes against that jamb aren't already fixed/window (reusing the batch-24 restriction pattern, not silently rewriting them), then tags that jamb `meeting` (see §2.6), creates elevation 2, and switches to it via the existing tab UI. Hard-capped at 2 elevations; "Add angled join" disappears once elevation 2 exists, replaced by "Remove angled join" (deletes elevation 2 after a confirm prompt and restores the jamb). **Batch 35 added the join's own stored angle** — creation now has a second step (angle entry, 90–180°, no default) after jamb selection, and a persistent input next to "Remove angled join" allows editing it afterward; removal resets it. **Batch 36 added a third field, the joint's construction type** (`angledJoinType`, null | 'butt' | 'mitred') — creation now has a third step (joint type, no default) after angle entry, with its own persistent editing control and its own reset on removal, same pattern throughout. **Batch 39 built the last remaining piece of §7.4's original spec, the cross-elevation pane-to-pane link** — computed fresh at export time only (no stored field, no UI), pairing each elevation's meeting-jamb-touching panes top-to-bottom; see §6.7 item 1 and §7.4 below for full detail. §7.4's original four-question spec is now fully built.
 
### 2.2 — The tree
 
A single rectangular region is recursively divided by a binary tree of nodes:
 
- `{kind:'empty'}` — an unassigned region.
- `{kind:'filled', type, productClass, sashTopMM, sashBottomMM, sashLeftMM, sashRightMM, sashTopLocked?, sashBottomLocked?, sashLeftLocked?, sashRightLocked?, hingeEdge?, slideDirection?, bladeWidthMM?, bladeLengthMM?}` — an assigned pane. See §2.3 for the current type vocabulary and §2.5 for the per-edge sash dimensions. **The `sash*Locked` fields (batch 23) mark an edge as part of an unframed silicone joint — protected from the manual uniform sash-width input; only cleared by removing the joint itself.**
- `{kind:'split', axis, posMM, thicknessMM, children:[a,b], hingedDoorRef?, assemblyPresetRef?, isSiliconeJoint?}` — a division into two children. `hingedDoorRef` and `assemblyPresetRef` are markers stamped at creation time so the tree can be walked back up to find "is this part of a hinged door" or "is this part of a built preset assembly" without re-deriving it from shape. **`isSiliconeJoint` (batch 23) distinguishes a genuine unframed silicone joint (`thicknessMM:0`) from an ordinary zero-thickness split created for another reason (casement's no-mullion toggle, a sliding flush join).**
- `{kind:'sashSplit', axis, fromEdge, sashSizeMM, overlapMM, children}` — the original overlap-sash mechanism, kept, not discarded.
Splitting always divides an existing region into two. No free-form x/y placement.
 
### 2.3 — Pane types
 
Six types:
 
| Type | Meaning |
|---|---|
| `fixed` | No sash frame of its own — glass runs to the pane's own edge |
| `fixed-framed` (label: "Fixed (sash)") | Non-operable, but has a real sash frame band, same as any operable type. Window/side-panel only — excluded from doors |
| `hinged` | `hingeEdge: 'left'\|'right'\|'top'\|'bottom'`. Covers casement and awning as one underlying type |
| `horizontal-slider` | `slideDirection: 'left'\|'right'` |
| `vertical-slider` | `slideDirection: 'up'\|'down'` |
| `louvre` | `bladeWidthMM`, `bladeLengthMM` stored — captured for the future AS 1288 blade-envelope check, not yet wired into rendering realism |
 
Toolbar-level restriction, not a data-model restriction: the door group's "Hinged" button and the window group's "Casement" button both produce `type:'hinged'`, restricted to `hingeEdge: 'left'|'right'` only. A separate "Awning" button produces `type:'hinged', hingeEdge:'top'` directly, with no edge dropdown shown. `hingeEdge:'bottom'` is supported in the data model but unreachable from any button.
 
Two toolbar rows — "Door panels" (fixed, hinged, horizontal-slider) and "Window sashes" (fixed, fixed-framed, hinged/casement, awning, horizontal-slider, vertical-slider, louvre).
 
**Batch 24 restriction:** a pane with any `sash*Locked` edge can only ever be `type:'fixed', productClass:'window'` — every other type button (including the Door group's own "Fixed" button, since that's `productClass:'door'`) is disabled while a lock is present. See §2.10 for the full mechanism.
 
### 2.4 — productClass and nesting inside a hinged door
 
Every filled node carries `productClass: 'door' | 'window' | 'side-panel'`. `side-panel` is supported in the data model but not settable from any toolbar button — reserved for a future derivation rule (§6.3), not a manual choice.
 
Nesting a sash inside a hinged door panel: splitting a hinged door panel allows `louvre`, `vertical-slider`, and `hinged` (only when `hingeEdge:'top'`, i.e. the Awning button) as children — `horizontal-slider` and side-hung `hinged` are blocked. `fixed` is always allowed as a child and renders with no frame band of its own. Any type assigned while nested under a hinged door has its `productClass` forced to `'door'`, regardless of which toolbar group the button came from — opening type (door/window/side-panel) is independent of glazing method.
 
The hinge symbol for a split hinged door spans the entire original door panel, not the individual leaf — `walk()` tracks every split node's own rectangle, not just leaf rectangles, and finds the nearest hinged-door ancestor to size the symbol against. A nested Awning sash still draws its own hinge symbol in addition — only a plain `hingeEdge:left/right` leftover (the un-nested continuation of the door's own glazing) is suppressed in favour of the door-spanning symbol.
 
Hinge symbol rendering: two full-corner-to-opposite-midpoint SVG lines (replaced an earlier CSS border-triangle) — apex points away from the hinge edge.
 
### 2.5 — Per-edge sash frame dimensions and glazed area (batch 9)
 
Every filled pane stores four independent values — `sashTopMM`, `sashBottomMM`, `sashLeftMM`, `sashRightMM` — replacing an earlier single uniform `sashFrameMM`. The toolbar still shows one input ("Sash frame width (mm)"); typing a value writes all four fields equally, **skipping any edge marked `sash*Locked` (batch 23)** — for manually created/edited panes.
 
**Batch 16 addition — real per-type default shape for preset-created panes:** `PRESET_SASH_EDGES = {sashTopMM:60, sashLeftMM:60, sashRightMM:60, sashBottomMM:86}`, sourced from Duce's own dimensional data (§7.1), is stamped on every casement and awning leaf built via the assembly-preset mechanism (`buildCasementPresetTree`/`buildAwningPresetTree`). This does **not** change the manual toolbar path (`makeTypeButton`), which still uses the uniform `DEFAULT_SASH_MM` fallback for hand-assigned/edited panes — the distinction is deliberate: only a *preset* stamps the real per-type shape at creation, per this batch's own instruction. Double-hung is explicitly excluded from this batch's per-edge treatment — see §2.9's double-hung note below.
 
A separate `glazedAreaM2(leaf)` computes true glass area (pane size minus the four sash values), shown in an additive pane-table column, labelled **"Visible glazed area (m²)"** (renamed from "Glazed area (m²)" in batch 28 — label only, `glazedAreaM2()`'s computation is unchanged) — the original "Area (m²)" column (full outer pane area) is unchanged.
 
**A locked edge (batch 23) always has an effective sash value of `0` on the touching side, by construction of how the joint is created — see §2.10.**
 
### 2.6 — Outer frame
 
Head/sill/jambL/jambR, independently editable, off by default. **Batch 26 built the per-elevation-edge override this section used to say didn't exist:** each elevation now also carries a `meetingEdges` tag (`{head, sill, jambL, jambR}`, each `null` or `'meeting'`) plus a matching `meetingLink`. A meeting-tagged edge is forced to 0 by `getMembers()` regardless of `hasFrame`, and its input/on-drawing label are locked, independent of the whole-elevation `hasFrame`/`frameMembers` toggle described above. Only `jambL`/`jambR` are reachable from the UI ("Add angled join," §7.4) — `head`/`sill` exist in the data shape (so turning them on later is UI-only) but have no UI path in this batch.
 
### 2.7 — Master dimension flip
 
The entered overall width/height are the outer frame's own outside dimensions. The opening is derived: `openingW = overallW − jambL − jambR`, `openingH = overallH − head − sill`. Changing a frame member cascades a recursive minimum-pane-size validation (`validateTreeAgainstSize`) against every descendant, blocking the edit inline if anything would shrink below `MIN_PANE_MM`. This validation function is reused directly by the assembly-preset reopen mechanism (§2.9).

**Batch 28 — height is shared between joined elevations.** Width (`overallW`) stays fully independent per elevation, confirmed and unchanged. Height (`overallH`) is now synced for as long as an angled join exists: creating the join (`addAngledJoin`) copies elevation 1's current height onto the newly created elevation 2; after that, editing the height field on **either** elevation while a join exists propagates the new value to the other elevation's stored `overallH` too — both fields stay independently editable, there is no primary/secondary side. `handleOverallInput`'s height path now validates the new height against **both** elevations' own trees (each against its own frame members, via a generalized `getMembers(ev)` that defaults to the active elevation) before committing either one; if either elevation's tree would fail (`MIN_PANE_MM` or `validateTreeAgainstSize`), the whole change is blocked and rolled back, even if the elevation being edited would itself have been fine. With no join present (single elevation), this is an unchanged no-op. The width path (`isWidth: true`) was not touched.
 
### 2.8 — Dimensioning
 
AS 1100 chain dimensioning: when multiple splits along one axis would produce colliding on-screen labels, later ones stack into additional rows further from the drawing. Pane dimension labels and the door/window (D/W) selected-pane indicator both show only when that pane is currently selected, not unconditionally by on-screen size.
 
### 2.9 — Assembly presets (batches 10–22)
 
A way to generate a full multi-section horizontal layout (or, for double-hung, a two-level stacked layout) in one action, instead of manually splitting and assigning each section by hand.
 
**Entry point:** a categorized, icon-based picker — no typed pattern entry anywhere (an earlier free-text field was fully removed, not left as a fallback). Icons are auto-generated small SVG previews reusing the same visual language as the main drawing, via a shared family-aware dispatch mechanism (`getPresetSectionCount`/`buildPresetTree`/`renderIconForPreset`) so each family's builder/icon logic is a swappable implementation behind one dispatch point.
 
**Families, as currently built:**
 
- **Sliding doors** — OX, OXX, OXXO, XOX, OXXX, OXXXX, OXXXXX. `O` → `fixed`, `X` → `horizontal-slider`. - **Sliding windows** — OX, OXX, OXXO, XOX, OXXX (five — no OXXXX/OXXXXX window variant, and no window OXO, confirmed against Duce's actual price list, §7). `productClass:'window'`. **Batch 17:** the 4 core `-win` ids (`OX-win`, `OXX-win`, `XOX-win`, `OXXO-win`) build with a genuinely different internal structure from a plain flat-row split. **Batch 18:** `OXXX-win` — left on the old plain-split path after batch 17 as an open question — is now folded into the same treatment too, as a consistency call (not independently re-confirmed). Every sliding window and door id now shares one mechanism; see the dedicated "Sliding overlap + frame tuck-in" write-up below.
- **Casement** — `C` (single), `CCset` (two, same hinge direction), `CCpair` (two, mirrored outward), `CCCCset` (**new in batch 16** — four sashes, all same hinge direction, no mirroring; `CASEMENT_HINGE_EDGES['CCCCset'] = ['left','left','left','left']`), `CCCCpair` (four, as two independent mirrored pairs). Window-only.
- **Awning** — A, AA, AAA, AAAA. All sections `hingeEdge:'top'`.

The person can still freely edit any prefilled value before confirming, same as always. A sliding id has no mullion input at all in its widths form (its joins are overlap/flush, never a separate mullion member) — its entered-total check instead uses `computeSlidingWinTotalWidth` (sum of section widths, minus 60mm per real overlap join, minus the flat 40mm tuck-in when `hasFrame` is true). **Data model — stored on the existing filled leaf, not a new tree node kind.** `doorPanelStyleId` (e.g. `'D1'`) and `doorPanelZoneChoices` (an object keyed by a stable `rowIndex_colIndex` zone id, valued with the chosen material) live directly on the `kind:'filled', productClass:'door', type:'hinged'|'horizontal-slider'` leaf. A door panel with a style applied is still fundamentally a normal filled door leaf — this keeps it automatically restricted to an unsplit door leaf with zero extra gating code, since a `split`/`sashSplit` node is a structurally different `kind` entirely and can never carry these fields. `canHaveDoorPanelStyle(node, hingedDoorAncestor)` gates the picker: `kind:'filled'`, `productClass:'door'`, `type` hinged or horizontal-slider, AND not itself a nested Awning sash inside another hinged door panel (that combination can also satisfy `type:'hinged'`+`productClass:'door'` per the existing `hingedDoorAncestor`/`hingeEdge:'top'` forcing rule — batch 31 traced this edge case and explicitly excluded it, since a nested Awning insert is a window-style sash, not the door panel itself).

**Catalog shape (`DOOR_PANEL_CATALOG`).** Each style is an ordered list of row bands (top to bottom): a FIXED band (a rail, fixed mm height) or a CONTENT band (a proportional share of remaining vertical space, fixed at the style's own reference-size proportion). Each content row holds an ordered list of column segments (left to right), same fixed-vs-content rule horizontally. A content column segment is an actual zone — `'fixed-glass'`, `'interchangeable'` (with a catalog-defined option list, one of which may be `'glazing'`), or `'solid-panel'` — while a fixed segment is a stile/glazing bar with no zone at all. Confirmed to represent every shape found across the real product range: a single lite (D1), multiple stacked fixed lites, a true row/column grid (D6), and interchangeable zones (D22).

**Geometry engine (`computeDoorPanelLayout`) — genuinely live, called fresh every render.** Sums fixed row-band heights, subtracts from the leaf's CURRENT `h` to get remaining content height, and distributes that across content rows in proportion to each row's own share of remaining height AT THE REFERENCE size (not equal shares). Same logic for columns within a row, using the leaf's current `w`. Deliberately its own function, not `walk()` and not `sashSplit` — a fixed-members-plus-proportional-gaps grid is structurally different from a binary split tree, and reusing either would have forced an awkward fit (`walk()` untouched, verified by inspection — no code path in this batch touches it). Hand-traced and numerically verified for all 3 styles, both at reference size and resized larger/smaller: fixed members stay exactly their stated mm width in every case, and content proportions hold exactly (e.g. D22's two interchangeable rows stay at a 1090:570 ≈ 65.7%:34.3% split at any panel height).

**Rendering.** A styled leaf renders its own live grid (a `.pane` background of `var(--frame)` for fixed bands/segments, with absolutely-positioned child divs for each zone) instead of the normal fixed-pane/sash-band drawing — a new branch in the same per-leaf render loop, gated on `l.node.doorPanelStyleId`. `fixed-glass` and `interchangeable`-currently-glazing zones draw as glass (`var(--glass)`); `interchangeable`-currently-timber and `solid-panel` zones draw as timber (`#8a5a2e`, close to but distinct from the frame's own `#f47920` so a zone reads as infill rather than structure). The pane's existing dimension label / D-class-letter and (for horizontal-slider/hinged) slide-arrow/hinge-symbol overlays are unaffected — those are drawn by separate, unmodified code that runs regardless of which background branch fired.

**Picker UI (`renderDoorPanelStylePicker`/`renderDoorPanelStyleIcon`).** Reuses the assembly-preset picker's own icon-button visual language (`.preset-icon-btn`/`.preset-icon-label`, same auto-generated-SVG-icon approach as `renderIconForPreset`) rather than its specific preset-family logic, per this batch's own instruction. A new "Choose door panel style" toolbar button (relabels to "Door panel style: D22" etc. once one is applied) opens the picker; selecting an icon stamps the style and, for a style with interchangeable zone(s), shows a follow-up material `<select>` per zone (options are the style's own catalog list) — deliberately a simple control, not styled to match the icon picker. D1/D6 (pure fixed-glass) show no follow-up at all, since there's nothing to choose.

**Explicitly out of scope for batch 31, not started at the time:** the remaining ~30 real door styles; any export-schema representation of a door panel's individual glazing zones (a styled panel still exports as one aggregate pane via the existing pipeline, unchanged — each zone's own dimensions are real future work); the free-form "cut your own opening in a timber panel" idea from an earlier session, now superseded by this catalog-based approach entirely.

10. **Batch 17 (sliding-window overlap) — two real design bugs caught and fixed during implementation, before either could reach the committed code as silent breakage.**
    - The original batch prompt asserted the overlap-sash's "sash is always `children[0]`" as a fixed geometric rule. Tracing `walk()`'s actual `sashSplit` branch line-by-line showed this only holds for `fromEdge:'start'` — `fromEdge:'end'` puts the sash at `children[1]`. The actual rule implemented: `fromEdge:'start'` when the sash is the physically-left leaf of a join, `fromEdge:'end'` when it's the physically-right leaf.

### 6.7 — Schedule integration with the AS 1288 human-impact check — planning session, nothing built yet
 
Captured in a chat session on 17 September 2026, prompted by a direct question about integrating a version of this configurator into the AS 1288 tool's own human-impact check. **Nothing in this subsection has been implemented. It's a design record, same status as any other addendum in this document.**
 
**The actual feature, as described by the person:** instead of the AS 1288 tool checking individual glass panels one at a time, it would let the user build a full window/door **schedule** — a list where each item may be a real combination of windows and doors (their own examples: "Awning-fixed", "Hinged door with sidepanels and highlights above"). For each schedule item, this configurator would be used to build the elevation **as close to the real product as possible** — i.e. the full tool, not a simplified/watered-down version, per the person's own direct confirmation when asked which they meant. The AS 1288 human-impact engine would then read, per item: the real dimensions, whether each pane is a window/door/sidelight, and additional schedule-level data (FFL, and **room type** — a genuinely new data point, not previously captured anywhere in this project) to determine whether human-impact/safety-glass requirements apply.
 
**What this reuses, already fully specified — nothing new to design:**
- **Sidelight determination** — exactly §6.3's existing door/side-panel/window classification rule. The person's own phrase, "sidelight determination based on calculations from dimensions," is a restatement of that rule, not a new requirement.
- **FFL** — already decided (§6.5) to live on the AS 1288 tool's own schedule-row form, not in the configurator.
**What's genuinely new:**
- **Room type** as a schedule-row data point, alongside FFL — not previously mentioned anywhere in this project before this session.
- **A single system holding more than one elevation** (§2.1) — clarified this session (see §1, §11) as squarely this configurator's own job to build, not something to push onto the AS 1288 side. Still entirely unbuilt.
- **The schedule list itself** — a list of many schedule items, each its own system, each potentially holding one or more elevations — **this list-holding is the AS 1288 tool's job, not the configurator's** (see §1's scope clarification, and item 2 below on storage).
**Three separate decisions, deliberately kept apart rather than treated as one "integration" task:**
 
1. **Export — v1 built (batch 29), following §6.1's existing principle; bumped to v2 in batch 39.** Schema designed and recorded in `configurator_export_schema.md`. A plain, generic serialization of what's already on screen per elevation — flat pane list (position converted to bottom-left-from-main-origin, Y up; type/productClass/hingeEdge/slideDirection/blade dims as stored; area/visible glazed area; per-edge sash widths; `unframedEdgeCount` combining both the Case-2 `sash*Locked` flags and Case-1 meeting-jamb-touch geometry), plus a computed `frameLengthMM` per elevation (sash perimeter + real mullions/transoms + outer frame, summed to `totalFrameLengthMM` at the system level) — no AS 1288-specific derivation logic baked into the configurator itself; the actual side-panel/sidelight derivation (§6.3) still runs on the receiving end, exactly as already decided. Correct regardless of which elevation is active when exporting (traced both ways).

**Batch 39 — schemaVersion 2, the pane link ships, angle/joint-type join `system`.** `system` now carries top-level `angledJoinAngleDeg`/`angledJoinType` (null on a single-elevation system) — previously held back in `rawState` only since batches 35–37, deliberately, until this pane link could ship alongside them, per this section's own standing note. Every pane gets a `linkedPaneId`. **The pane link is computed fresh at every export, directly from geometry — it is NOT a stored field anywhere, no new tree-node field, no UI to create/manage/edit it, nothing that can go stale.** For each elevation, whichever `meetingEdges` entry is actually tagged `'meeting'` is found independently (never assumed to be a fixed jambL/jambR pair — `addAngledJoin` always tags the two elevations' OPPOSITE jambs, checked per elevation via the same `MEETING_EDGE_UI_JAMBS` list `addAngledJoin`/`removeAngledJoin` already iterate), and that elevation's meeting-jamb-touching leaves are collected via a fresh `collectExportGeometry` pass (never the render-time `ev.lastLeaves` cache, which is only valid for whichever elevation last rendered). Every touching leaf is already guaranteed `type:'fixed', productClass:'window'` by the existing `leafAllowedAgainstMeetingEdge` join-creation/edit blocking rule, so no new type restriction was needed. The `ready` postMessage handshake's own `schemaVersion` was bumped to 2 to match. No change to `rawState`/`rawStateSchemaVersion` — those stay exactly as batch 37/38 left them.

**Batch 40 — correctness fix: matching is by actual edge position, not sorted order + array index.** Batch 39's own original pairing (quoted above, now superseded) sorted each elevation's touching panes top-to-bottom and linked them purely by index — first-with-first, second-with-second. **This was a real bug, found and fixed in batch 40, a configurator-side correctness finding, not a change requested by the AS 1288 side:** two elevations can have the same pane count in the same top-to-bottom order while the panes' actual edges along the jamb don't line up at all (e.g. a transom at 1000mm on one elevation's meeting edge, 1400mm on the other's) — index-pairing would silently link two panes that don't physically meet. Fixed: each touching pane's start/end position along the jamb (its own internal `y`/`y + h` — the same coordinate already used to detect touching, not a second coordinate system) must both match a pane on the other side before the two are linked. **This subsumes the old count-mismatch check** — a bare count mismatch is now just one way a pane can end up with no matching partner, so there's a single per-pane match check rather than two separate checks. The blocking error now names the elevation and the specific mm range with no match, plus the closest candidate found (if any). **UI:** export-blocking errors now also show in a new box directly next to the Export/Done button (`#exportError`), in addition to the existing top-of-page banner (kept, since it's also used for batch 38's schema-mismatch-on-load case, which fires before the button is a meaningful place to look) — both fire together via new `showExportBlockedError()`/`clearExportBlockedError()` functions.

**Batch 41 — correctness fix: the matching tolerance itself was wrong.** Batch 40 used `EDGE_TOUCH_EPS_MM` (0.01mm) for the start/end comparison above — flagged at the time as reused rather than the batch prompt's own "1mm" suggestion, kept for "one touch-tolerance concept throughout the file." **That reuse turned out to be the wrong call:** `EDGE_TOUCH_EPS_MM` exists to absorb floating-point noise within ONE elevation's own clean tree arithmetic ("does this pane touch the jamb at all"), not to judge whether two independently-computed mm values from two DIFFERENT elevations' trees represent the same physical edge — 0.01mm is unrealistically tight for physical timber joinery and risked false-blocking a genuinely valid export over ordinary float drift. Fixed with a new, separate constant, `PANE_EDGE_MATCH_TOL_MM = 1`, used only in `matchesEdge()`'s two comparisons; `EDGE_TOUCH_EPS_MM` itself and every other call site of it (jamb-touching detection, `unframedEdgeCount`) are unchanged — grep-confirmed. Batch 40's three reported test cases were re-traced against the new tolerance and produce identical pass/block outcomes (round numbers 400mm apart aren't affected by a 1mm-vs-0.01mm tolerance either way).

**Batch 43 — schemaVersion 3, expose `sashless` per pane.** Every leaf built by a sashless preset (batch 42, §2.9) already carried an internal `sashless:true` flag, but it was never exported — `sashEdgesMM`'s literal values alone can't reliably distinguish "built by the sashless preset checkbox" from "someone manually typed small sash numbers." `buildExportElevation` now adds `sashless: !!node.sashless` to every pane — a direct, undecorated read of the existing flag, no new logic, no derivation. Every pane not built by a sashless preset (including every pane that existed before batch 42) exports `false`. Same precedent as batch 39: an additive change to `system`'s own pane shape, not `rawState`, gets a real `schemaVersion` bump — the `ready` postMessage handshake's own `schemaVersion` was updated to match. No change to how sashless panes are created (batch 42), to `rawState`/`rawStateSchemaVersion`, or to the cross-elevation pane-matching logic (batches 39–41).

**Batch 44 — schemaVersion 4, per-edge `unframedEdges` breakdown.** `unframedEdgeCount` (batches 23/26/30) sums three sources without saying which specific edges are unframed — AS 1288 needs the actual edges, since Table 5.3 governs vertical/jamb-side edges and a different clause governs horizontal edges, and a bare count can't distinguish the two. `buildExportElevation` now also computes `unframedEdges: {top, bottom, left, right}` from the exact same three sources (`sash*Locked` → Case 2, meeting-jamb-touch → Case 1, `fixed`-on-`hasFrame:false` → Case 3), mapped per-edge rather than summed. **Sashless exception, applied only to `unframedEdges`:** if `node.sashless === true`, `top` and `bottom` are forced `false` regardless of what the three-source computation produced — a sashless pane's rail-free horizontal edges are represented solely by `sashless:true` (batch 43), never doubled up via `unframedEdges`. `left`/`right` are untouched by the exception, so a sashless pane's stile touching a meeting jamb still reports that edge correctly. **`unframedEdgeCount` itself received no change at all** — it keeps summing all three sources exactly as before, including for sashless panes, so a sashless `'O'` (fixed) panel on a `hasFrame:false` elevation can end up with `unframedEdgeCount` counting all 4 edges while `unframedEdges`'s own true-count is only 2 (left+right). This is a deliberate, documented inconsistency between the two fields in that one specific overlap case, not an oversight — see `configurator_export_schema.md`'s own field notes. Same precedent as batches 39/43: an additive change to `system`'s own pane shape gets a real `schemaVersion` bump — the `ready` postMessage handshake's own `schemaVersion` was updated to match.

**Batch 45 — correctness fix: bare O panels, plus a fourth `unframedEdges` source (Case 4). No `schemaVersion` bump — corrects the existing v4 shape, doesn't add a new field.** Two parts. **(1)** `buildAssemblyPresetTree` was wrongly stamping a sashless O (`type:'fixed'`) leaf's `sashLeftMM`/`sashRightMM` with `SASHLESS_STILE_MM`, same as an X leaf — but a bare fixed pane has no sash material at all, so it's now zeroed on all four edges for O specifically, matching an ordinary non-sashless O exactly; X leaves are unaffected, still `SASHLESS_STILE_MM`. Double-hung confirmed unaffected by direct inspection — `buildDoubleHungUnit` never builds a `type:'fixed'` leaf at all, so this branch is structurally unreachable there. **(2)** A new Case 4 on `unframedEdges` only (never `unframedEdgeCount` — a second, independently-documented divergence between the two fields, distinct from batch 44's sashless top/bottom exception, not to be merged with it): a sashless O leaf's edge at an internal sliding-window overlap join (touching a sashless X sibling) is now flagged unframed, since fix (1) means that edge genuinely carries zero sash material. Gated strictly on the leaf's own `node.sashless === true && node.type === 'fixed'` — never the neighbour's value, since sashless-ness applies uniformly across the whole preset. Detected by reading `buildSlidingWinOverlapTree`'s actual confirmed output structure (traced through `collectExportGeometry`'s `sashSplit` branch, not guessed at): sibling leaves at an overlap join genuinely overlap in x by the sliding-overlap distance (not merely touch at a near-zero gap, which is why this uses real x-range + y-range intersection against every other leaf in the elevation's own `leaves` list, not an `EDGE_TOUCH_EPS_MM` adjacency check) — left/right decided by which side the matched neighbour's center falls on. O-O adjacency, which would make left/right ambiguous, is confirmed impossible for every pattern `classifySlidingWinJoin` actually handles (it throws rather than guess on that case). Confirmed by inspection: casement/awning build plain mullion splits with no overlap joins at all, so this can never fire there; a non-sashless O next to a non-sashless X is completely unaffected, gated out entirely by the `sashless === true` check — genuinely framed by real sash material in that case.

**Batch 46 — correctness fix: sashless flag removed from O, Case 4 gate moved to the neighbour. No `schemaVersion` bump.** Physical product confirmed directly by the person (not derived): a sashless O's top, bottom, AND outer jamb edge are all genuinely frame-supported by real timber — only its inner vertical edge, facing a sashless X, is completely unsupported (no channel, rebate, bead, or silicone at all there). `sashless: true` means "this pane's horizontal edges are unsupported, route to AS1288 Clause 5.15" — true for a sashless X, false for a sashless O. ### 7.4 — Case 1 (angled/multi-elevation) — resolved specification, mostly built (captured 18 September 2026; join mechanism + stored angle built batches 26/35)
 
This section supersedes the original four open questions raised in §7.3 — all four are now answered, and all four are now built: §2.1's multi-elevation capability (batch 25), the join mechanism itself (batch 26), the stored angle value (batch 35), and — the last one — the cross-elevation pane-to-pane link (batch 39, see item 1 below). §7.4's original spec is complete.
 
**Important scope correction made mid-session, recorded here so it isn't reintroduced (see also §1, §11):** it was briefly, incorrectly reasoned that because "the configurator works on one system at a time," pane A (elevation 1) and pane B (elevation 2) of an angled product must live in entirely separate sessions with no shared memory — and therefore the cross-elevation link (below) couldn't be the configurator's responsibility. **This is wrong and was corrected directly by the person.** Pane A and pane B are always the *same* system — "one system at a time" means the configurator doesn't hold a *list* of many different schedule items open at once (that's the AS 1288 tool's own job); it does not mean one system is capped at one elevation. Once built, the configurator itself is exactly the tool responsible for holding and editing both of one system's linked elevations together, in one session.
 
**The four original questions, resolved:**
 
1. **Does the tool need to remember the link between pane A and pane B?** Yes — confirmed as a real requirement. **Built, batch 39 — but not the way originally assumed:** the decision made when this batch was scoped was that the link is NOT stored anywhere at all (no new tree-node field, no UI to create/manage/edit it) — instead it's computed fresh, directly from geometry, on every single export. For each elevation, whichever `meetingEdges` entry is tagged `'meeting'` is found independently (never assumed to be a fixed jambL/jambR pair), and that elevation's meeting-jamb-touching panes are collected; each pane's export gets a `linkedPaneId` (or `null`). **Batch 39's original matching rule (sorted position + array index) was a real bug, found and fixed in batch 40:** two elevations can have the same pane count in the same top-to-bottom order while the panes' actual edges along the jamb don't line up (e.g. a transom at 1000mm on one side, 1400mm on the other) — index-pairing would silently link panes that don't physically meet. Batch 40 fixed this to match on actual edge position (both start and end) instead; any pane with no matching partner (a bare count mismatch is now just one way this can happen — folded into a single check) blocks the entire export, naming the specific mm range with no match, in both standalone and embed mode. **Batch 41 corrected the tolerance batch 40 used for that matching** — `EDGE_TOUCH_EPS_MM` (0.01mm) was reused at first, but that constant exists for a different, more forgiving purpose and was unrealistically tight for judging whether two independently-computed mm values represent the same physical edge; replaced with a new, dedicated `PANE_EDGE_MATCH_TOL_MM = 1` constant used only for this comparison. Both fixes were configurator-side correctness findings, not changes requested by the AS 1288 side. Full detail in `configurator_export_schema.md`'s "Cross-elevation pane link" and "Export blocked on an unmatched meeting-jamb pane" sections.
2. **How does a person create the second, linked elevation?** Resolved implicitly: since a two-wall angled product is one system with two elevations (not two separate systems referencing each other), "create a second elevation" isn't a joint-specific mechanism — it's the general "add another elevation to this system" capability that §2.1's own multi-elevation work needs to provide regardless of the joint feature. No dedicated joint-specific button or screen needs designing here.
3. **Does the angle number need to be stored?** Yes — confirmed as real data, not reference-only. **Built, batch 35:** a system-level `angledJoinAngleDeg` field (null when no join exists, a number 90–180 once one does), captured as a required second step of "Add angled join" (after jamb selection, no default value) and editable afterward via a persistent input next to "Remove angled join." No geometric effect on rendering. **Exported as of batch 39** — a real top-level `system.angledJoinAngleDeg` field in the export schema (v2), shipped alongside the cross-elevation pane link (item 1 below) as originally planned, not released piecemeal.
4. **Do both walls share the same FFL?** Yes, one shared value per system — and, confirmed again specifically for this case, entirely out of the configurator's own scope: FFL is entered once on the AS 1288 tool's own schedule-row form (§6.5), covering the whole system regardless of how many elevations it has.
