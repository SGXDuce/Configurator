## 1. What this is and why it exists

A standalone, browser-based configurator for building up a window/door elevation: an opening, an optional outer frame, and a recursively-divided grid of panes, each assignable as a fixed panel, a hinged panel, a horizontal or vertical sliding sash, or a louvre. Every dimension is shown directly on the drawing and is editable there.

**It grew out of, but is now deliberately separate from, the AS 1288 Glass Thickness Calculator project at Duce Timber Windows and Doors.** That project's "window schedule" feature (a list of windows/doors for a job, each broken into systems and then panes for compliance calculation) needed a way to actually lay out a system's glazing — this configurator is that layout tool. It is explicitly **not** being built as a calculator-specific feature. The intent is a standalone tool other tools can consume:
- The AS 1288 compliance engine (needs per-pane span, aspect ratio, and support condition).
- A future pricing/quoting tool (needs per-pane glass area, frame linear lengths, and counts).

Neither consumer's exact data needs have been designed against yet — this is currently a pure drawing/geometry tool with no export schema.

**Open strategic question, not resolved, worth raising again before real investment:** Duce has (or had) a Logikal vendor evaluation in progress — Logikal is a commercial fenestration ERP with its own parametric configurator and quoting built in. There's also a separate, parked initiative to standardize sales-to-production drawing handoff via Autodesk Fusion 360. Building this configurator in-house may duplicate either. This was flagged before prototyping began; the user chose to proceed with a prototype anyway, but the question hasn't gone away for a real build.

**Current state of the actual artifact:** a single self-contained HTML file (`configurator_prototype_oxxo.html`), vanilla JS, no frameworks or build step, no backend, no persistence. Nothing here is wired into the AS 1288 Flask app or any other tool. It was built entirely inside a Claude chat (not Claude Code), iterated live against screenshots the user sent back after each round of testing.

## 2. Data model

### 2.1 — The two-level concept this sits inside (upstream context, not literally coded yet)

The broader "window schedule" concept this configurator serves is two levels:
- **Opening** — a schedule row / job line item (e.g. "W01").
- **System(s)** — one or more glazed units within that opening (e.g. a door + sidelight is two systems).

The configurator prototype itself works on **one system/frame at a time** — it does not yet model multiple systems or an opening-level schedule. That's still to be connected.

### 2.2 — The tree, as actually built

A single rectangular region (the opening, or the frame if one's been added) is recursively divided by a binary tree of nodes:

- `{kind:'empty'}` — an unassigned region: needs a type or a further split.
- `{kind:'filled', type, productClass, sashTopMM, sashBottomMM, sashLeftMM, sashRightMM}` — an assigned pane.
  - `productClass` ∈ `'door'` | `'window'` | `'side-panel'`; it is a manual label, not inferred from geometry.
  - `type` ∈ `'fixed'` | `'fixed-framed'` | `'hinged'` | `'horizontal-slider'` | `'vertical-slider'` | `'louvre'`.
  - `sashTopMM` / `sashBottomMM` / `sashLeftMM` / `sashRightMM` — the visible width of that pane's own sash frame band, stored **per edge** (batch 9; previously one uniform `sashFrameMM` field applied to all four edges — see below), default 40mm each. `fixed` panes have no sash frame at all; these fields simply aren't populated/relevant for them.
- `{kind:'split', axis, posMM, thicknessMM, children:[a,b]}` — a division into two children.
  - `axis`: `'v'` (vertical/mullion-style, divides width) or `'h'` (horizontal/transom-style, divides height).
  - `posMM`: distance from the region's own left/top edge to the divider's centreline. **Always stored this way internally**, regardless of which edge the user actually measured from when they typed it in.
  - `thicknessMM`: width of the member. **Zero is valid** — see "plain split" below.
  - `children[0]` = near side (left for axis `v`, top for axis `h`); `children[1]` = far side.
  - `hingedDoorRef?: { hingeEdge }` — present only when this split was created by dividing a hinged door panel (`productClass:'door', type:'hinged'`), or by dividing something already inside one. Stamped by `confirmSplit` at the moment of splitting, since the door's own `productClass`/`type` no longer exist at this path once it's a `split` node — this is how the door's single ancestor-level hinge symbol (Section 2.4) finds its way back to the door's hinge edge after the door itself stops being a leaf.
  - `assemblyPresetRef?: { pattern, productClass }` (batch 12) — present only on the top-level split of a tree built by an assembly preset (Section 2.9). Stamped at creation time, same precedent as `hingedDoorRef`; it's the only way to find and reopen that subtree's widths form later, since a preset-built tree is otherwise indistinguishable from a hand-built one once created. Deliberately never stores `family` (batch 13) — reopening re-derives it from `pattern` via `detectPresetFamily`, since `pattern` alone is enough (a plain O/X string vs. a recognised casement/awning id).

**Splitting always divides an existing region into two — there is no free-form x/y placement anywhere.** This was a deliberate call: recursive subdivision guarantees every layout tiles with no gaps or overlaps by construction, which is both simpler to validate and matches how real fenestration is actually built (a grid of mullions/transoms), unlike a true CAD-style free-placement canvas, which would need separate overlap/gap detection and was judged not worth the risk for this stage.

**Splitting an already-assigned ("filled") pane is allowed** — both children inherit the parent's type by default, representing subdividing one sash's own glazing with a decorative bar, not creating two separate operable units. Either side can then be reassigned independently.

### 2.3 — Three ways to divide a region, same underlying mechanism

- **Add mullion / Add transom** — a `split` node with a real, user-specified `thicknessMM`: an actual frame member, drawn solid.
- **Split vertical (no member) / Split horizontal (no member)** — a `split` node with `thicknessMM` forced to 0: identical position logic, nothing drawn at the boundary. Intended for a boundary that doesn't need its own frame piece (e.g. two sashes' own frames meeting).
- **Overlap-sash history:** a dedicated "add sash" action where a sash carries its own overlap depth and interlocks into its neighbour is retained as a distinct `sashSplit` node type with asymmetric, overlapping child geometry. It remains a supported division mechanism alongside mullions, transoms, and zero-thickness plain splits.

### 2.4 — Pane types

| Type | Meaning | Needs a real member on every side? |
|---|---|---|
| `fixed` | Plain fixed panel, **no sash frame of its own** — glass runs straight to the pane's own edge | Yes — always, since it has nothing of its own to seal against. **Not currently enforced by the tool.** |
| `fixed-framed` (labelled "Fixed (sash)" in the UI) | Non-operable, but **has a real sash frame band** around it, same as any other type. **Windows/side-panels only — not offered for `productClass:'door'`.** | No — can sit against a zero-thickness split |
| `hinged` | Hinged pane; `hingeEdge` records the hinge edge | No — can sit against a zero-thickness split |
| `horizontal-slider` | Horizontal sliding sash; `slideDirection` records `'left'`/`'right'` travel, shown as a single ← or → arrow | No — can sit against a zero-thickness split |
| `vertical-slider` | Vertical sliding sash; `slideDirection` records `'up'`/`'down'` travel, shown as a single ↑ or ↓ arrow — same pattern as `horizontal-slider`, added after `vertical-slider` initially shipped with a fixed two-way ↕ arrow and no stored direction | No — can sit against a zero-thickness split |
| `louvre` | Louvre pane | No — can sit against a zero-thickness split |

`fixed` and `fixed-framed` are deliberately two separate types, not a toggle on one type: `fixed` is frameless (glass to its own edge) and is available for doors, windows, and side-panels alike; `fixed-framed` ("Fixed (sash)" in the UI) is non-operable but framed like a real sash, and is **windows/side-panels only** — it is not offered for `productClass:'door'` at all, in the toolbar or in the valid-combinations table. The overlap-sash system's "Fixed (non-operable)" dropdown option always creates `fixed-framed`, never plain `fixed` — an overlapping sash without its own frame to interlock with its neighbour doesn't make sense (that dropdown is reached from any pane, including a door's, since the overlap-sash mechanism itself isn't productClass-gated — its resulting pane is always tagged `productClass:'window'` regardless of what it overlaps into, which is a known simplification, not a deliberate design position).

`hinged` covers both casement (side-hung, `hingeEdge` `'left'`/`'right'`/`'bottom'`) and awning (top-hung, `hingeEdge:'top'`) as one type in the data model — awning is not a separate type, and this has not changed. The hinge symbol is two thin unfilled lines running the pane's full corner-to-corner extent: both corners on the hinge edge connect to the midpoint of the edge directly opposite, forming a V with its point away from the hinge (hinge on the left → lines from the top-left and bottom-left corners meet at the midpoint of the right edge, etc.). This replaced an earlier small inset CSS-triangle symbol.

**Hinge UI is more restricted than the data model:** although `hingeEdge` still supports all four values internally, the toolbar only ever offers `'left'`/`'right'` via a "Hinged" button (in both the Door panels and Window sashes groups) and `'top'` via a separate "Awning" button (Window sashes group only — awning doors aren't offered). Selecting "Awning" always assigns `hingeEdge:'top'` directly and, when that pane is selected, the toolbar shows no hinge-edge dropdown at all (nothing to choose — it's always top). The "Hinged" button's dropdown offers only left/right. `hingeEdge:'bottom'` is not reachable from any toolbar control in this batch, though a node that already has it (e.g. from earlier data, or a future change) is still rendered and handled correctly — it's just not currently creatable via the UI.

**Valid `type` × `productClass` combinations, enforced in the UI:** `productClass:'door'` accepts `fixed`, `hinged`, `horizontal-slider` only (**not** `fixed-framed`, `vertical-slider`, or `louvre`); `productClass:'window'` or `'side-panel'` accept all six types.

Type buttons are assignable via the same direct-assign toolbar buttons on any empty region, **regardless of which split mechanism created that region** — this is looser than the mid-project design intent (originally, sash-carrying types were only going to be reachable via the dedicated sash-insertion action); after that action was removed, the type/mechanism link was never re-tightened for the general case. Worth revisiting: see Section 5.

**Exception — nesting inside a hinged door panel:** the toolbar *does* restrict which types are offered when the selected empty region's parent chain includes a `productClass:'door', type:'hinged'` ancestor (i.e. the region was created by splitting a hinged door panel). In that case only `fixed`, `louvre`, `vertical-slider`, and `hinged` with `hingeEdge:'top'` (the awning case) are offered — `fixed-framed` (already excluded from doors entirely), `horizontal-slider`, and side-hung `hinged` are disabled, since they aren't physically sensible as sashes let into a door leaf's own glazing. `fixed` children of a door panel render with no sash band of their own (frameless), same as any other `fixed` pane. Each other nested type still gets its own sash frame band drawn inside the door's own band where applicable (band-within-band).

**Hinge symbol spans the whole door leaf, not the individual child region.** When a hinged door panel is split to hold a nested sash, the door's own hinge symbol is drawn once, sized to the door panel's full original rectangle — ignoring the internal division — not once per child leaf. This was confirmed against a supplied reference image (a hinged door with a louvre insert draws one hinge line pair across the whole leaf). Splitting a node replaces it with a `kind:'split'` node, so the door's own `productClass`/`type` data is gone from that path once split — a `hingedDoorRef: {hingeEdge}` marker is stamped directly onto the split node at the moment a hinged door panel (or something already inside one) is divided, so the fact survives structurally. `findHingedDoorAncestor` walks up looking for that marker; `walk()` records every node's own rectangle (not just leaves), keyed by path, so the marked ancestor's rect stays available even though it's no longer a leaf. An unsplit hinged door renders its own symbol exactly as any other hinged pane does (leaf and ancestor are the same rectangle in that case). See Section 3 for the first, non-working attempt at this and why it silently did nothing.

**Nested Awning still draws its own symbol.** The ancestor-level suppression only applies to a leaf whose `hingeEdge` is `'left'` or `'right'` — that's just the door's own continuing glazing, already fully represented by the door-level triangle. A deliberately nested Awning sash (`hingeEdge:'top'`) draws its own symbol *in addition to* the door's, the same way a nested louvre draws its own blade lines and a nested vertical slider draws its own arrow. (The first version of the ancestor-suppression logic suppressed any `type:'hinged'` leaf under a hinged-door ancestor regardless of `hingeEdge`, which wrongly hid a nested Awning's own symbol — fixed to check `hingeEdge` specifically.)

**"Hinged" vs "Casement" vs "Awning" — a display-label distinction only, not a new type.** The internal type string is always `'hinged'`; the label shown depends on context: `productClass:'door'` → "Hinged" (the door panel itself swings on hinges); `productClass:'window'`/`'side-panel'` with `hingeEdge:'top'` → "Awning"; `productClass:'window'`/`'side-panel'` with any other hinge edge → "Casement". A `getTypeLabel(type, productClass, hingeEdge)` helper centralises this — every place that displays a type name (toolbar buttons, the pane table's Type column) goes through it instead of a flat `TYPE_LABELS[type]` lookup, so the two don't drift out of sync again.

**Nested-in-door assignments are always `productClass:'door'`, regardless of which toolbar group offered the button.** Opening type (door/window/side-panel) is independent of glazing method — a door containing an operable window is still a door. Any pane assigned while nested inside a hinged door panel (louvre, vertical-slider, awning, fixed) is stamped `productClass:'door'` at assignment time even when clicked from the Window Sashes group (which normally sets `'window'`). This means the D/W letter and the pane table's Class column read "D" for a nested sash, not "W" — only `productClass` changes; the type label (previous paragraph) still shows the pane's own specific type. The overlap-sash ("Add sash") mechanism is not covered by this override — it isn't offered/disabled based on door-nesting context at all today, and always tags its result `productClass:'window'`; this is a known, pre-existing gap, not something this batch closed.

**Plain "Hinged" is disabled when nested in a door; Awning stays enabled.** The nested-in-door disable check originally always evaluated the hinge edge as `'top'` regardless of which edge the button actually assigns — meaning it always passed (top-hung is the one allowed hinged case), so the plain "Hinged" button (left/right) never greyed out even though it's not a valid nested assignment. Fixed to check the button's own effective hinge edge instead, consistent with Horizontal slider already being disabled in that context.

**Manual `productClass` and the two-group toolbar:** every filled pane also carries a `productClass` (`'door' | 'window' | 'side-panel'`), set manually — never inferred from geometry (except when nested inside a hinged door panel, where it's forced to `'door'` regardless of button group — see above). The toolbar exposes it as two button groups that set `productClass` and `type` (and, for hinged, a fixed `hingeEdge`) together in one click: **Door panels** (Fixed, Hinged [left/right], Horizontal slider) and **Window sashes** (Fixed, Fixed (sash), Casement [hinged, left/right], Awning [hinged, always top], Horizontal slider, Vertical slider, Louvre). "Casement"/"Awning" (window context) and "Hinged" (door context) all produce the same `type:'hinged'` — display-label-only distinctions, not separate types (see the hinge-label paragraph above). `side-panel` is a valid stored value and the type/productClass combination table above already accepts it wherever `window` is accepted, but no toolbar control sets it in this batch — it's expected to be assigned by some future rule/calculation, not chosen directly by the user here.

**Click-to-reveal class indicator:** when a filled pane is the currently selected one — the same condition that reveals its width × height label (Section 2.5) — a single centred letter also appears on its glass: `D` for `productClass:'door'`, `W` for `'window'` or `'side-panel'`. Not shown otherwise.

### 2.5 — Sash rendering ("hidden edge" convention)

- Every assigned pane's own outer edge is drawn **dotted** — representing the sash's true outer edge, which in a real elevation is hidden inside the surrounding frame/mullion/transom's own channel or rebate.
- Inside that, a **solid** orange band is the sash's own visible frame face, with each of its four edges drawn at that edge's own stored width (`sashTopMM`/`sashBottomMM`/`sashLeftMM`/`sashRightMM` — CSS `border-top-width` etc. individually). A `fixed` pane has no sash band and its glass runs to its own edge.
- Glass fills what's left inside the band.
- If a pane is too small on screen for the band to render meaningfully, it just fills flat with glass (display-only fallback, doesn't affect stored data); this fallback's own inset is computed per edge too, clamped the same way as the drawn-band path so both agree on where glass starts.
- The pane's own width × height label only shows when that pane is the currently selected one (previously it showed for any pane large enough on screen, regardless of selection).
- **Per-edge storage, single-input UI (batch 9):** the four sash edges are stored separately, but the toolbar still exposes only one "Sash frame width (mm)" input — typing a value sets all four to that same number (`withUniformSashMM`). There is no per-edge editing UI yet; this batch only laid the data-model and rendering groundwork (a deeper bottom rail, previously flagged as a likely future need, is now representable in the data, just not yet reachable from the UI).
- **Glazed area (batch 9):** the pane table has a new "Glazed area (m²)" column, separate from the existing "Area (m²)" column (which stays the full outer pane area, unchanged). Glazed width = pane width − `sashLeftMM` − `sashRightMM`; glazed height = pane height − `sashTopMM` − `sashBottomMM`; for `fixed` panes (no sash frame), glazed area equals the full pane area. The table footer totals both columns.

### 2.6 — Outer frame (optional, off by default)

- No frame exists until explicitly added, via an "Add outer frame" toggle — some real jobs are a bare opening with panels/sashes butted straight in, no surrounding frame.
- Once added, it has **four independently customizable members** — head (top), sill (bottom), left jamb, right jamb — not one uniform thickness. Each has its own input and its own on-drawing dimension (shown once large enough on screen to hold the text).
- The entered overall width/height are the outside dimensions of the outer frame when a frame exists. The opening is derived as `openingW = overallW - jambL - jambR` and `openingH = overallH - head - sill`; changing a member therefore shrinks the glazing area.

### 2.7 — Reference origin

- **Main origin** — always exists, cannot be removed. It's the frame's true outside bottom-left corner (outside the left jamb and sill) if a frame exists, or the opening's own bottom-left corner if not. Shown as a small grey dot labelled "main origin".
- **Custom origin** — user-settable two ways:
  1. **Click to place** — toggles a picking mode; the next click anywhere on the drawing (including directly on a frame member) snaps to the nearest corner or midpoint among the opening's corners/edge-midpoints, the outer frame's outside corners, and every pane/split's own corners and centre, within an 18px on-screen tolerance (otherwise it uses the raw click point).
  2. **Enter coordinates** — type an exact X (rightward) / Y (upward) offset from the main origin.
  - "Reset to main origin" clears the custom origin.
- **The origin is a single, frame-wide reference point for displayed dimensions** — split positions remain stored relative to their own region's left/top edge, while the active origin is used when entering and displaying those positions.
- Changing the origin re-labels every dimension live; it never moves anything.

### 2.8 — Dimensioning

- Overall width/height dimension lines use the **AS 1100 architectural convention**: extension lines with 45° oblique tick marks, not arrowheads (arrowheads are the mechanical/engineering convention under the same standard). Split dimensions chain outward from the drawing: each split's tick/label is placed in the nearest row (closest to the drawing) where it doesn't collide, on screen, with a label already placed in that row; colliding ones stack into additional rows further out. This is a simple greedy, position-based check — not a general constraint solver — and the drawing's own gutter grows to fit however many rows end up needed.
- **Every dimension on the drawing is double-click editable**: overall opening width/height, each of the four frame members, every mullion/transom/split's position, and every pane's own width and height.
  - Editing a pane's width or height works by walking up the tree to find the nearest ancestor split whose axis matches (`v` for width, `h` for height) and moving that split's position. If no such ancestor exists — the pane's size on that axis comes straight from the opening itself — the tool says so and points at the overall dimension instead, rather than silently failing or doing nothing.
- **"Show dimensions" toggle** hides/shows all of the above at once. The origin markers are deliberately **not** tied to this toggle (treated as a reference point, not a dimension) — this was a judgement call made while building, not something the user explicitly confirmed as final.
- Every edit is validated against a minimum pane size floor (`MIN_PANE_MM = 50`, a generic sanity floor, **not** a real hardware minimum) before committing; invalid edits show an inline error and don't apply.

### 2.9 — Assembly presets (batches 10–15)

A shortcut for building a full multi-section horizontal layout in one action, instead of manually adding a mullion and assigning each section's type by hand (the exact kind of manual-marking gap the door/side-panel `productClass` derivation elsewhere in this project exists to safety-net against). Built across six passes — the core mechanism (batch 10), the entry-point UI (replaced once, in batch 11), reopening an already-built one to resize it (batch 12), two new flat-row families reusing that whole mechanism unchanged (batch 13), the first genuinely two-level family (batch 14, double-hung — extends the tree-building/icon machinery but deliberately does NOT extend the reopen mechanism yet), and catalog-informed default section widths on fresh creation (batch 15).

**Entry point — categorized icon picker (batch 11; replaced batch 10's free-text pattern field entirely, no typing anywhere in this feature):** an "Apply assembly preset" button sits alongside Add mullion/Add transom/Add sash (overlap) in the toolbar for any selected leaf, filled or empty — same permissiveness as the direct-assign type buttons, which already overwrite a filled pane freely. Disabled (same styling as other disabled buttons in this context) when the selected region has a hinged-door ancestor, since sliding and casement sections are already disallowed as children of a hinged door panel (`isAllowedInHingedDoor`, checked at this entry point too). Clicking it shows `ASSEMBLY_PRESET_CATEGORIES` as data — a heading per category, a row of small auto-generated icon buttons underneath — iterated generically by the picker's render loop rather than any category being special-cased in that loop, so batches 13 and 14 could each append new categories without touching it.

**Categories (five, as of batch 14):** "Sliding doors" (7 presets, `productClass:'door'`, no `family` — defaults to the sliding/O-X family), "Sliding windows" (5 presets, `productClass:'window'`), "Casement windows" (`family:'casement'`: `C`, `CCset`, `CCpair`, `CCCCpair`), "Awning windows" (`family:'awning'`: `A`, `AA`, `AAA`, `AAAA`), "Double-hung windows" (`family:'double-hung'`: `D`, `DD`, `DDD`). `family` is what every dispatch point (section/unit count, tree building, icon drawing) branches on; its absence means the original sliding O/X behaviour, entirely unchanged from batch 11.

**Section inputs (sliding/casement/awning — unchanged since batch 10):** once a preset is chosen (or an existing one is reopened — see below), one width input per section plus one shared "Mullion thickness (mm)" input appear. Confirm validates that section widths + `(sectionCount − 1) × mullionThickness` exactly equals the assembly's own current width; a mismatch shows an inline error stating entered total vs. available width (same convention as `confirmSplit`'s own error) and applies nothing — the tool never auto-resizes to fit. Section labels read "Section N (O/X) width (mm)" only when `pattern` is actually a plain O/X string (`/^[OX]+$/`); casement/awning ids (`'CCpair'`, `'AAA'`, ...) aren't per-section letter sequences, so those fall back to a plain "Section N width (mm)" label rather than reading garbled individual characters off an opaque id.

**Double-hung's own inputs are shaped completely differently (batch 14), not forced through the section-by-section form above:** `renderDoubleHungPresetForm` — a shared "Unit width (mm)" applied to every unit, a shared "Top pane height (mm)" applied to every unit (the bottom pane's height is the derived remainder, `regionHeight − topHeight − transomThickness`, never entered separately), a "Transom thickness (mm)" (the internal divider within each unit), and a "Mullion thickness (mm)" shown only when the preset has more than one unit (`DD`/`DDD`) — same conditional-field precedent already used for the outer frame's own member fields toggling on `hasFrame`. No per-unit customisation of width/height/transom is offered at all, deliberately, unlike casement's independent per-section widths. `confirmDoubleHungPreset` validates the exact-match total (`unitWidth × unitCount + mullionThickness × (unitCount−1)` against the region's width) and, additionally, that both the top height and the derived bottom height are each `>= MIN_PANE_MM` and that transom thickness `> 0` — blocking inline with the same error convention as everywhere else if not.

**Catalog-informed default section widths on fresh creation only (batch 15).** `ASSEMBLY_PRESET_CATALOG_SIZES` is transcribed programmatically (not hand-typed, to avoid transcription error) from Duce's real NGR price list, current as at 01/10/2025 — every `sizesMM` entry is `[heightMM, widthMM]` for the assembly's whole total (not per-section; sections are equal-width by Duce's own convention), keyed by **preset id**, not pattern (`'OX'` sliding-door and `'OX-win'` sliding-window share a pattern string but have distinct catalog data, so `id` — already unique per preset button, and now carried through `chosenPreset` where it was previously discarded — is the correct key). `CCCCpair`, `AA`, `AAA`, `AAAA`, and a window-family `OXO` have no entry at all — deliberately, not an oversight. When the widths form first opens for a fresh creation (never `editAssembly` — reopening keeps pre-filling from live current widths exactly as batch 12 built it, untouched by this batch), `findClosestCatalogSize(id, actualHeightMM, actualWidthMM)` finds the nearest `[h,w]` entry by simple summed absolute difference (`|actualH−catH| + |actualW−catW|`, not height or width alone) and, if this preset id has any catalog data, pre-fills every section's width input with `matchedWidthMM / sectionCount` and shows a "Closest standard size: {h} × {w}mm" info line. These equal-split defaults will often not sum exactly to the region's actual width — intentional; the existing exact-match validation already prompts the person to adjust before confirming, unchanged. No catalog entry for this id (or editing mode) means the widths inputs and the info line are both left exactly as this batch's predecessor already left them — blank inputs, no line — verified by tracing `findClosestCatalogSize` returning `null` cleanly for `CCCCpair`. Mullion thickness gets no catalog-informed default at all, since the source data only ever reports total assembly size, never a member-thickness breakdown.

**Tree building, dispatched by family:** `buildAssemblyPresetTree` (sliding: `O`→`fixed`, `X`→`horizontal-slider`) is untouched from batch 10/11. `buildCasementPresetTree` and `buildAwningPresetTree` (batch 13) build `type:'hinged', productClass:'window'` leaves instead, sharing the same right-to-left v-axis fold (factored out as `foldSectionsIntoSplits`, used by all three builders — including the original, which now calls it too instead of duplicating the loop). `buildPresetTree(pattern, sectionWidthsMM, mullionThicknessMM, productClass, family)` is the single dispatch point `confirmAssemblyPreset` actually calls; `getPresetSectionCount(pattern, family)` is the equivalent for section count, since casement/awning ids encode their count by name (`CASEMENT_SECTION_COUNTS`/`AWNING_SECTION_COUNTS` lookup tables) rather than by string length. Every fresh leaf across all families gets default `sashTopMM`/`sashBottomMM`/`sashLeftMM`/`sashRightMM` = `DEFAULT_SASH_MM`.

**Default hinge edge — casement (`CASEMENT_HINGE_EDGES`):** `C` (single) → `'left'`, an arbitrary default — with only one section there's no natural reference point to mirror against, same reasoning as the sliding family's own no-O fallback. `CCset` → `['left','left']` (same direction, not mirrored). `CCpair` → `['left','right']` (mirrored outward from the shared centre). `CCCCpair` → `['left','right','left','right']` — **two independent pairs**, each mirrored outward from its own pair's centre, not one shared centre across all four.

**Default hinge edge — awning:** every section `hingeEdge:'top'`, no per-pattern lookup needed at all — awning has no direction ambiguity, unlike casement or sliding.

**Default slide direction — sliding only** (`computeDefaultSlideDirections`, unchanged): each `X` defaults toward its nearest `O` by index distance (`OXXO` → the two middle X's slide apart, each toward its own nearer flanking O; `XOX` → both slide inward toward the shared centre O; `OXXX`/`OXXXX`/`OXXXXX` → every X slides toward the single O). Two explicit edge cases: an exact tie between two equidistant O's defaults to `'right'` (an arbitrary tie-break, no physical convention behind it); a pattern with no `O` at all defaults every `X` to `'left'` (no natural reference point). This is only ever the *initial* value — the existing per-pane slide-direction dropdown still lets the person override any section individually afterward. Casement/awning's own per-pane hinge-edge dropdown works identically, unmodified, since these are just ordinary `type:'hinged'` leaves once built.

**Double-hung tree building (batch 14) — the first family whose "sections" aren't flat leaves.** Each unit is its own two-level subtree, built by `buildDoubleHungUnit`: `{kind:'split', axis:'h', posMM: topHeightMM, thicknessMM: transomThicknessMM, children: [top vertical-slider (slideDirection:'down'), bottom vertical-slider (slideDirection:'up')]}` — the two panes converge toward each other at the shared transom. `buildDoubleHungPresetTree` builds `unitCount` of these subtrees, uniform width/height/transom across all of them (per this family's own spec — no per-unit customisation, unlike casement), then folds them into a row via the exact same `foldSectionsIntoSplits` every other family already uses — that helper never cared what shape each "leaf" was, so passing whole unit-subtrees in as `leaves` needed no changes to it at all. Every leaf gets `productClass:'window'` and default `sashTopMM`/etc. = `DEFAULT_SASH_MM`, same as every other family. `buildDoubleHungPresetTree` is NOT routed through `buildPresetTree`'s dispatcher — its inputs (`unitWidth`, `topHeight`, `transomThickness`, `mullionThickness`) don't fit that dispatcher's `(pattern, sectionWidthsMM, mullionThicknessMM, productClass)` shape, so `confirmDoubleHungPreset` calls it directly.

**Double-hung icon (batch 14):** `renderDoubleHungPresetIcon(unitCount)` draws two STACKED boxes per unit (not a single row like every other family's icon), a `↓` in the top box and `↑` in the bottom — the same glyph convention already used for real vertical-slider arrows on the main drawing (`.slide-arrow`), just scaled to icon size, same principle as casement/awning reusing the real hinge-line geometry rather than inventing new iconography. `buildPresetIconBoxRow`'s single-row scaffold doesn't fit this two-tall shape, so this draws its own layout rather than reusing that helper.

**Icons, dispatched by family (sliding/casement/awning):** `renderPresetIcon(pattern, slideDirections)` (sliding — orange-outlined boxes, an arrow per sliding section) is unchanged. `renderHingedPresetIcon(hingeEdges)` (batch 13, casement and awning) draws the same box row via `buildPresetIconBoxRow(sectionCount)`, then the *real* corner-to-midpoint hinge-line shape (`hingeSymbolCorners` — extracted out of `buildHingeSymbol`, the function that draws actual hinge symbols on the main drawing) scaled to icon size inside each box, rather than a separate hand-invented preview language. This is what makes a `CCpair` icon visibly mirror outward while `CCset`'s icon shows both lines pointing the same way — confirmed by tracing the actual corner/apex coordinates each produces. `renderIconForPreset(pattern, family)` is the single dispatch point the picker's render loop actually calls, now covering all five families.

**Reopening to resize (batch 12; confirmed unmodified and working for the sliding/casement/awning families as of batch 13; deliberately NOT extended to double-hung in batch 14 — see below):** the top-level split of a preset-built tree is stamped with `assemblyPresetRef: { pattern, productClass }` at creation time (same precedent as `hingedDoorRef`, and used identically by double-hung too) — note this marker never stores `family`; reopening re-derives it via `detectPresetFamily(pattern)` (a plain O/X string → sliding; else looked up in the casement/awning/double-hung id tables — `'D'`/`'DD'`/`'DDD'` confirmed globally unique against every other family's ids, so no shape-based heuristic is needed). `findAssemblyPresetAncestor(path)` mirrors `findHingedDoorAncestor`'s walk-up pattern, with one deliberate difference: it keeps walking and returns the *innermost* marked split, not the first one found, since (unlike hinged doors) nothing stops a preset being built inside one section of another preset. When a leaf under a marked split (or the marked split's own bar) is selected, an "Edit assembly widths" button appears **unless the marker's family is `'double-hung'`, in which case it's omitted entirely (not shown-disabled — just absent)** — the existing reopen mechanism (`confirmAssemblyEdit`, `getAssemblyLeafNodesInOrder`, `getAssemblyPresetCurrentState`) all assume a flat single row of leaves, and double-hung's two-level shape needs that mechanism properly extended in its own batch, not retrofitted here. For every other family, clicking it jumps straight to the width-inputs step (no picker), pre-filled with:
  - **Section labels** from the marker's stored `pattern` — plain-O/X-string check applies here too (same fallback as fresh creation, described above), so a reopened `CCpair` shows generic "Section N" labels, not garbled characters. This reflects the *original* pattern; a section's current type may have changed individually since creation — an accepted minor cosmetic gap, not solved.
  - **Current widths and mullion thickness**, recomputed live from `lastNodeRects` (every node's rect from the most recent render, not just leaves — added in batch 12 alongside the pre-existing leaf-only `lastLeafRects`, specifically so a section that's since been subdivided further still reports its true current combined width instead of being missed) — never cached creation-time values, so a mullion moved individually via the ordinary dimension-edit mechanism is reflected correctly. Mullion thickness is read from the marked split's own `thicknessMM` only (not averaged across the chain, even if individual mullions have since gone non-uniform).
  - Confirming an edit (`confirmAssemblyEdit`) rebuilds the same right-to-left fold at the new positions/thickness but reuses each section's *existing* leaf node exactly as-is (type, productClass, direction, sash values, anything nested underneath) — only `posMM`/`thicknessMM` change. `validateTreeAgainstSize` (built for the frame-dimension-flip work) checks every nested descendant still fits at `MIN_PANE_MM` under the new widths before committing, blocking inline with the standard error convention if not.

**Out of scope so far:** reopening/editing an existing double-hung assembly's dimensions (see above — deliberately excluded, not forgotten), any per-unit customisation of double-hung's width/height/transom (deliberately uniform across all units, per that family's own spec), any change to the outer frame (head/sill/jambs), vertical/transom-based presets for the other families, mixing letters across families in one pattern, and any change to how the marker behaves for a section that's been subdivided further (the marker only ever governs the outer chain's own widths).

## 3. Real bugs found and fixed during this build

Worth knowing so they aren't reintroduced by a future rewrite:

1. **Frame border eating into content space.** The outer frame's border was originally drawn inward without compensating for its own thickness, so panes sized for the full nominal opening overflowed past the visible border by the border's own width. Fixed by adding the border thickness back onto the container's box so the content area always equals the nominal size exactly.
2. **Fixed pixel-scale rendering overflowing the browser window.** The mm-to-pixel scale was originally a constant, so a large enough opening would eventually overflow the page no matter how wide the page was made. Fixed by computing the scale live from the actual available container size (and recomputing on window resize) — widening the page alone (tried first) wasn't sufficient.
3. **Origin-click not registering on the frame member itself.** Clicking a pane or a mullion/transom worked for placing a custom origin, but clicking the outer frame's own member (head/sill/jamb strip) did nothing — those areas had no element with a click handler attached. Fixed by moving origin-placement handling to the top-level drawing container's own click handler, computed from the container's own bounding box rather than the inner opening container.
4. **Double-click-to-edit unreliable.** A native `dblclick` fires after two ordinary `click` events. Those clicks were bubbling up to the drawing's own click handler, which redraws the entire elevation on every plain click (to support "click empty space to deselect") — destroying the element being double-clicked before the second click could register as part of a double-click. Fixed by stopping propagation on any plain click landing on an editable dimension label.
5. **Slider arrows piling up at the same vertical position.** `.slide-arrow` set only `left`/`width` per pane and relied on a single fixed `top: 50%` in CSS to vertically center itself — but that 50% was relative to the whole diagram container, not to the individual pane. Every horizontal- and vertical-slider arrow in the elevation therefore rendered at the opening's own mid-height regardless of which pane it belonged to, so sliders at different vertical positions had their arrows visually overlap/stack on top of each other (this was not a DOM-accumulation bug — each render cleared and rebuilt the diagram correctly, and each pane only ever produced one arrow of its own; the arrows were just all drawn at the same place). Fixed by setting `top`/`height` per arrow to the pane's own vertical extent and centering the glyph within that box via flexbox, matching how `left`/`width` already scoped it horizontally.
6. **Hinge symbol shrinking to the wrong rectangle once a hinged door panel was split — two attempts to fix this.**
   - **First attempt (did not work):** the hinge symbol was drawn per-leaf, keyed to whichever individual leaf still had `type:'hinged'`. The first fix tried to find a hinged-door ancestor by walking up the path looking for a `kind:'filled', productClass:'door', type:'hinged'` node — but this is structurally impossible to find once the door has actually been split: splitting a node **replaces** it in place with a `kind:'split'` node (its own `productClass`/`type` data is gone from that path entirely, surviving only as copies on the two children via `cloneForSplit`). A node can never simultaneously be `'split'` (to have children) and `'filled'` (to be the door), so the ancestor search always returned nothing, and every leaf under a split door kept drawing its own individual symbol exactly as before — the fix silently did nothing.
   - **Actual fix:** `confirmSplit` now stamps the new `split` node itself with a `hingedDoorRef: {hingeEdge}` marker at the moment a hinged door panel (or something already inside one) gets divided, so the fact "this subtree was a hinged door" survives structurally rather than needing to be re-derived from a node shape that no longer exists. `findHingedDoorAncestor` now walks up looking for the nearest `split`/`sashSplit` node carrying that marker. `walk()` was extended to record every visited node's own rectangle (not just leaves), keyed by path, so the marked split node's full rect stays available for the ancestor-level symbol even though it's no longer a leaf. The hinge symbol is drawn once per marked ancestor at that ancestor's own rect, and suppressed on individual leaves underneath it. An unsplit hinged door (leaf and "ancestor" are the same node) is unaffected; a plain hinged window with no door-panel involvement is likewise unaffected.
7. **Louvre blade lines offset asymmetrically within the glass area — two attempts to fix this.**
   - **First attempt (wrong root cause):** diagnosed as the small-pane fallback path using a flat, `sashFrameMM`-independent inset. That was a real but separate, minor issue (now also fixed) — it did not explain the reported symptom, which turned out to occur in the *normal* drawn-band path, not the fallback.
   - **Actual root cause, found by hand-tracing exact pixel coordinates against a real reproduction case:** the blade SVG is a child of the `.sash-band` div. CSS absolute-position offsets on a child are relative to the nearest positioned ancestor's **padding-box** — and `.sash-band`'s own padding-box (`box-sizing:border-box`, `border: insetPx`, no padding) already excludes its border. The code additionally offset the blade SVG by `insetPx` on top of that, double-counting the border and shifting the whole blade rectangle `insetPx` off-centre — flush against the border on one edge, with an `insetPx`-sized gap on the opposite edge, instead of symmetrically filling the band's true glass interior. Fixed by using an offset of `0` for the blade SVG when it's a child of `.sash-band` (whose padding-box *is* the glass rectangle already); the separate fallback path, where the blade SVG is appended directly to the pane (no intervening `.sash-band`, so no border to double-count), keeps its own `sashFrameMM`-derived offset from the first fix.
8. **Assembly preset pattern field would have lost keyboard focus on every keystroke (caught before shipping, batch 10; the whole field was removed in batch 11, so this fix no longer exists in the code — recorded for history only).** The pattern input validated live and called `render()` on every `input` event so the section-width inputs could appear/disappear as soon as the pattern became valid — but `render()` rebuilds the whole toolbar DOM from scratch, including recreating that same text input, which would silently drop focus and cursor position after every single character typed (a classic vanilla-JS re-render pitfall). Fixed at the time by capturing `selectionStart` before the re-render and re-focusing the freshly-created input with the same cursor position afterward; moot once the free-text field itself was replaced by the icon picker.
9. **Assembly widths form would never have rendered when reopened via "Edit assembly widths" (caught before shipping, batch 12).** `renderToolbar()` bails out immediately with a generic hint whenever `selected` is falsy, and separately returns unconditionally for `selected.isBar === true` — both checks run *before* `pendingSplit` is ever looked at. The button's first draft set `selected = null` (later `{isBar:true}`) when opening the edit form, which meant the toolbar would short-circuit into one of those early returns and never reach the `pendingSplit.mode === 'editAssembly'` branch that actually renders the form. Fixed by pointing `selected` at the marked split's own path with `isBar:false` — a synthetic, non-leaf "selection" that satisfies both guards without ever being looked up as a real leaf — and clearing it back to `null` on cancel (confirming already cleared it).
10. **Recomputing an assembly's current section widths would silently under-report a section that had been subdivided further (caught before shipping, batch 12).** The first draft looked up each section's current width via `lastLeaves.find(...)` for that section's exact leaf path — but if a section was individually subdivided after the preset was built, that path is no longer a leaf at all, so the lookup returned `undefined` and the width silently became `0` in the "available width" total and the form's own validation baseline. Fixed by adding `lastNodeRects` — a rect for every node `walk()` visits on each render, not just leaves (mirroring what the hinge-symbol ancestor lookup already needed in batch 6) — and looking sections up there instead, so a subdivided section still reports its true current combined width.

## 4. Component visual language

Reference schematics were supplied by the user (Duce's own visual convention, not this project's invention): sliding sash (orange frame, cyan glass, directional arrow), fixed panel (same, no arrow), transom (horizontal orange bar, no glass), mullion (vertical orange bar, no glass). Colour values used in the prototype: frame `#f47920`, glass `#5be3ea` — sampled to match the supplied images, not necessarily Duce's official brand values.

Louvre, casement, and awning (as `hinged` with `hingeEdge:'top'`) are now handled — see Section 2.4. "Sashless" glazing is still not a modelled concept in this configurator. Note that the parallel human-impact-engine work on the AS 1288 project already has its own input model for opening type (window/door/side panel) and glazing method (fixed panel/sash, louvre, sashless) — if this configurator is ever wired into that engine, the two models will need to be reconciled; they were built independently and haven't been checked against each other. The `productClass` field (Section 2.4) is a first, deliberately minimal step toward reconciling the window/door/side-panel half of that — it doesn't yet reconcile glazing method / sashless.

**Legend temporarily removed.** The on-page legend (a key mapping swatches/symbols to each pane type and split mechanism) has been removed entirely, markup and code both — not fixed or partially cleaned up, just taken out. This is deliberate and temporary: the type system has been changing batch to batch (new types, the fixed/fixed-framed split, the hinged/awning toolbar split), and the legend was being rewritten every time to chase it. It will be rebuilt once the type system stabilises.

## 5. Known gaps and open items

- **No enforcement that a plain `fixed` panel always sits next to a real mullion/transom.** You can currently assign it next to a zero-thickness split, which isn't physically correct. Flagged repeatedly during the build, never solved — would need validating both sides of a boundary together, which today's per-pane validation doesn't do.
- **No hardware or manufacturability constraints** — no minimum real-world sash width, no maximum mullion spacing, no structural sizing check. `MIN_PANE_MM = 50` is a sanity floor only.
- **No connection to the AS 1288 pathway engine, the Flask app, or any backend.** Purely client-side, nothing persists between browser sessions.
- **No drag-and-drop anywhere.** Every position, member size, and pane dimension is a typed number, either at creation or via double-click afterward — never a dragged handle. This was an explicit, deliberate scope cut early on and was never revisited.
- **Unconfirmed engineering assumption:** every assigned pane is currently treated as fully framed on all four edges (equivalent to Pathway 1 in the AS 1288 tool) — including, implicitly, edges that are zero-thickness splits. This has not been checked against AS 1288 or confirmed with Michael (Duce's engineering domain authority), and is especially questionable for the zero-thickness-split case.
- **Resizing a split doesn't re-validate deeply nested descendants beyond the immediate min-pane-size check** — not a problem today since child sizes are always derived live at render time rather than cached, but worth re-checking if a future version introduces cached/absolute child sizes.
- ~~Shrinking the derived opening after components no longer fit is validated~~ **Fixed.** Editing overall width/height or any frame member now walks the whole tree and blocks the edit inline (same error styling as other invalid edits, value rolled back) if any descendant would drop below `MIN_PANE_MM`.
- **The link between split mechanism and pane type has loosened.** Originally, sash-carrying types were meant to be reachable only via a dedicated sash-insertion action; once that action was removed (Section 2.3), all four types became assignable via the same generic buttons regardless of mechanism. Worth a deliberate decision on whether to re-tighten this.
- **No export schema.** Nothing here has been designed against what the AS 1288 engine or a pricing tool would actually need to consume (per-pane span/aspect ratio/support condition; per-pane glass area; frame linear lengths and counts). Purely a drawing tool today.

### Future scope — not built

- Multi-select several openings in a job and assign a type to all of them at once. This needs a schedule/job-level data model above the current single-system tool, which does not exist yet.

## 6. Working style this was built with

Built entirely inside a Claude chat session (not Claude Code), as a single self-contained HTML file, iterated live: each round of user feedback (usually a screenshot of the rendered tool) led to a targeted root-cause diagnosis and a full-file rewrite, re-verified by parsing the embedded JavaScript with Node before being handed back — not accepted on faith that the rewrite was correct. The user's usual pattern (chat for architecture and prompt-drafting, Claude Code for real implementation with minimal hands-on coding) was deliberately not used for this phase; this was disposable, rapid prototyping specifically to nail the interaction model before any real build begins.
